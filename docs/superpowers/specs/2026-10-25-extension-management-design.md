# Nema 扩展管理设计

状态：已确认，按本文件实现。日期：2026-10-25。另一会话继续数据迁移之后的 9b 和任务 10。图标在 100%/150%/200% 下的实机检查留到本次扩展重构结束后一起验收。

## 已确认的需求

用户要求重构目前的「插件」页，使其实际管理 Skills、MCP 和插件，而不仅是展示固定工具列表：支持安装、卸载、启用、状态查看；安装来源包括原始 GitHub 仓库、Vercel Skills/skills.sh 等 Skills 来源；聊天中安装的项目也应在这里出现。Graphify 等内置组件应随应用提供并默认开启，不再要求用户自行执行 uv 安装命令。

用户已选择：**Nema 专属安装，兼容发现外部项**。Nema 管理自己的安装目录；发现的其他应用或共享目录中的项目可接入，但不由 Nema 删除其原始文件。

GitHub 不再提供 Nema token 输入表单。独立进行的本机 gh 接入复用 gh 已有登录；MCP 管理能力可在本设计落地后承载其他 GitHub MCP 连接。Workspace 创建反馈、模型连接下拉改版和已有桌面功能继续保留。数据迁移、完整回归和发布验证等原计划事项不被本设计取消。

## 现状与需要改变的部分

目前 PLUGINS 是固定清单；页面把 installed、登录状态和错误文本混在一起。Graphify 从系统 PATH 查找，因此桌面包内缺少依赖时出现“未安装：请运行 uv…”；Archify 和 Superpowers 规则已随包提供。内置 Agent 只声明固定 Room/插件工具，并没有通用的 Skills 发现、MCP 配置、安装记录或管理操作。

因此本次需要应用运行层、安装/发现服务、Agent 接入、打包和 UI 的配套改造，不能只把静态列表改成卡片。

## 方案与控制器的技术选择

考虑过：按 Skills/MCP/插件分别实现三个管理器；或共用扩展记录、安装任务和权限状态，再由类型适配器处理各自加载方式。前者初期较快，但聊天安装与页面状态容易产生不同记录。**本设计建议后者**，与用户选定的 Nema 专属安装范围结合。

统一的是来源、版本、安装归属、操作进度、启停和错误记录；Skills 的指令加载、MCP 的连接协议、Nema 插件的功能组合仍然分开。页面不是把三者都伪装成同一种可执行程序。

## 页面与核心交互

保留现有侧栏入口，页面标题改为「扩展管理」。页面提供：已安装、发现与安装；类型筛选为全部 / Skills / MCP / 插件；搜索名称、描述或来源。

每个项目显示名称、类型、用途、来源/原仓库、版本或固定提交、安装归属、作用范围，以及独立的状态：

- 提供方式：随应用提供 / Nema 安装 / 外部发现。
- 安装状态：未安装 / 安装中 / 已安装 / 更新中 / 卸载中 / 失败。
- 使用状态：启用 / 停用；MCP 另显示未连接 / 连接中 / 已连接 / 需要登录 / 连接异常。
- 可用性：依赖齐备 / 缺少依赖 / 版本不兼容 / 文件损坏。

不能把“程序存在但未登录”写成未安装，不能在成功状态旁继续展示过期的失败文本。技术诊断放在可展开的详情中，主要提示按当前界面语言显示。

安装入口接受 GitHub 仓库或 skills.sh 链接，识别可安装的 Skills/包后让用户选择。MCP 另支持添加启动配置或服务器地址。显示将安装的名称、版本、来源和 Nema 目标目录，再进入有进度、取消、失败原因及重试的任务。没有标准安装信息的仓库应说明需要哪些配置，不把 README 中的任意命令直接当作安装程序执行。

内置项目提供启停和修复/恢复内置版本操作；不提供删除应用内文件的“卸载”。Nema 安装的项目可卸载。外部发现的项目提供接入/移出 Nema 和打开来源信息，移出时保留外部原件。启用安装和 workspace 作用范围分别显示。

## 安装来源与版本

Skills 至少支持标准 SKILL.md GitHub 仓库（单 Skill 与多 Skill 仓库）、仓库子目录，以及 skills.sh/Vercel Skills 可解析的来源。记录原始仓库、所选 Skill、解析到的不可变提交、文件摘要和许可证/来源信息。只安装实际选择的内容与必需资源。标准格式 Skill 不要求作者为 Nema 另写一份插件。

MCP 支持本地 stdio 和远程 HTTP 配置。标准注册信息或已识别的 npm/PyPI/GitHub 安装描述转成明确的安装/启动配方；没有可识别描述时提供配置导入或手动启动配置。来源安装与服务器连接是两个步骤，远程服务不伪装成本地已安装包。第三方 Nema 插件使用版本化声明清单，可组合 Skills、MCP 和已有 Nema 功能适配器；不承诺任何任意 GitHub 项目都可一键变为插件。

安装后固定解析到的版本/提交，检查更新与执行更新分开。首次打开应用不联网补装内置依赖；用户主动安装或更新扩展时才进入相应下载任务。具体打包版本、资源下载/缓存、支持的清单字段由实现调查和计划确定，并记录为构建输入。

## 统一安装记录和操作服务

运行层维护版本化扩展记录：稳定 ID、类型、来源、版本/提交、归属、安装目录、作用范围、启用状态、所需能力、依赖、连接配置引用、最近操作及错误。实际安装目录与记录共同校验，保留可恢复的安装/卸载日志。

在 Nema 数据目录下划分受管扩展区、下载/暂存区和旧版本区。下载及校验在暂存区完成，通过后原子激活；失败保留已可用版本。跨应用升级保留已安装扩展、聊天和知识数据。重启能识别未完成任务并明确恢复、重试或取消，不把部分安装当作成功。

同一扩展的修改串行化。安装、更新、卸载的实际文件操作由本机运行层执行；Web 只提交固定管理操作并读取状态，不获得任意文件或进程接口。卸载只处理记录证明归 Nema 管理的版本目录，验证路径、链接和目录归属；聊天/知识/工作区数据与外部共享安装不在删除范围。

安装任务、元数据索引、扩展启用及 MCP supervisor 与现有单核心/数据库写入租约保持一致。关闭窗口继续后台任务；明确退出应用时取消/排空受管操作并保留可恢复状态。

## 界面安装、聊天安装与外部发现

页面按钮与聊天中的明确安装/卸载请求调用同一服务，产生同一种任务和安装记录。聊天显示来源、目标、进度与结果卡片，页面收到状态事件立即更新。Skills/MCP 返回的内容本身不能授权新的安装或扩大执行权限；缺少来源或操作含义不明确时，在聊天中补全明确的用户请求。

Agent 接入需要实际新增受限的扩展管理工具，而不是让模型通过任意 shell 修改系统目录。安装完成后，在后续任务中加载新 Skill/工具；当前任务固定使用已取得的扩展版本。卸载/停用先禁止新调用，停止相关 MCP/安装子进程并明确处理中断的调用，再释放文件；不默默重做任务或丢弃知识写入。

发现机制扫描 Nema 受管目录及用户选择/已知兼容位置，重新校验实际文件，支持刷新和变化通知。因此经聊天或兼容 CLI 安装到可发现位置的项目也能出现，即使安装动作不是从页面按钮发起。外部项记录真实来源/路径和外部归属，不自动搬走原件。

对 Codex/Claude Code/共享 Skills 等兼容来源，读取元数据或用户选定的配置入口；不遍历整台电脑，不把其他客户端的秘密作为可显示配置复制。外部 MCP 的“配置已发现”不等于“已经连接/授权”；某些客户端专属 OAuth 需要在 Nema 中建立自己的连接，不能承诺通用凭据共享。

## Skills 与 MCP 如何真正可用

Skills 按类型载入名称/描述与所需正文/资源，以渐进方式加入当前 Agent，而非一次把全部文本塞入提示词。已有 Claude Code 运行方式与 Nema 内置 Agent 都必须明确支持范围；若某项目需要当前运行方式没有的能力，应显示缺失能力，不能仅因安装成功就显示可用。

MCP 配置记录受管可执行包或显式启动参数、远程地址、连接范围、必要环境/凭据引用。凭据由本机受信任层保管，界面只得到已配置状态；不返回明文。MCP 工具经过连接、schema 校验、工具命名空间和显式启用后加入 Agent 的工具集合。已有 workspace、仓库范围、外部数据流和工具开关规则继续适用，第三方 annotations 不作为权限保证。

每个 MCP/安装进程使用现有受管 helper 所有权机制，配置变更与卸载会停止对应实例，退出/崩溃不能遗留失控进程。程序版本、连接状态和登录状态分别展示；应用不能因为缺少某个可选扩展而整体无法启动。

## 内置默认项与 Graphify

Graphify、Archify、Superpowers 的 Nema 规则包、Grill 等现有本地核心能力随应用交付并默认启用。内置规则包按 Nema 实际支持的版本和功能描述，不把现有精简规则包谎称为完整上游 Skills 全集。

Graphify 改为受管内置运行依赖：在构建期准备兼容版本及 Python/本地依赖等必要运行环境，打包、许可和来源记录进入现有产物清单；运行时使用明确的随包路径，用户无需全局 Python/uv。没有系统 Python/uv/graphify 的干净目标环境中，实际完成代码索引/检索等已支持功能，才算内置交付成功。内置缺失时显示可修复的包异常，而不是要求用户自行执行终端安装命令。

GitHub 接入器随应用提供，默认通路复用本机已登录 gh；gh 本身及外部账号不是 Nema 自建的 token 登录体系。`gh` 是否装好、是否已登录、连接是否可用，只交给 Nema Agent 在调用时判断。插件页和 workspace 设置不显示这些状态，也不提供让用户去登录、粘贴令牌或查看 `gh` 诊断的入口。用户仍可启用或停用该 workspace 的 GitHub 插件，并用 `allowWrites`（默认关）决定 Agent 能否写入。仅打开管理页不会自动读取远端 PR/Issue。安装 MCP 后也不自动放开所有外部或写入工具。Agent 经受控 `gh` 命令写 GitHub 是已存在的例外：仅当 workspace 打开 `allowWrites` 才提供，且命令限于白名单与绑定仓库（见 codebase-and-plugins-design 第 6 节）。

## 验证与交付边界

验证必须覆盖：界面和聊天安装同一项目后记录一致；GitHub/skills.sh 单仓库多 Skill 安装；升级/失败回滚/中断重启/取消；Nema 卸载与外部移出不会越界；外部安装的发现/刷新；Skills 实际加载；本地及远程 MCP 实际发现/启用/停止；凭据不回显；工具作用范围保持；Graphify 在无全局依赖下真实可用；中日英及窄窗口操作反馈。

开发验证只用明确的临时目录、假安装源/假 MCP/假凭据，不调用真实用户账号，不写入其他应用的配置，不影响已有品牌改版文件。桌面原有的启动、托盘、关闭/退出、独立核心、数据持久化、模型设置及 workspace 创建反馈都需要回归。跨平台运行/打包门槛保留，不能以 Windows 结果宣称 macOS 或 POSIX 清理已经通过。

原有数据迁移、完整测试及来源/发布门槛继续开放；本设计不是发布批准。具体落地顺序建议：统一记录/内置目录 → Skills 安装与加载 → MCP 配置/运行 → 页面与聊天统一操作 → 外部发现/导入引用 → 内置 Graphify 交付与完整 UI/打包验收。独立的 gh 接入继续先行。

## 已由用户决定与待实现调查的事项

用户决定：三类扩展统一管理；支持安装/卸载；原仓库与 Vercel Skills 等来源；聊天安装可见；内置项随包默认开启；Nema 专属安装、外部发现兼容；GitHub 复用本机 gh，由 Agent 调用。`gh` 的安装和登录状态不在界面显示，也不对用户开放连接入口。workspace 仍可启用 GitHub，并用 `allowWrites` 控制写入。

控制器建议：统一记录/任务服务加类型适配器；保留侧栏入口、页面命名扩展管理；外部项以引用方式接入；先落地标准 Skills 和声明式 MCP/插件来源，未识别来源显示所需配置；内置包不从应用目录卸载；外部访问沿用 workspace 开关。上述建议可在设计确认时调整。

留给实现调查：兼容版本/包清单、Graphify 的完整运行依赖与目标平台产物、各兼容客户端可发现路径和配置格式、MCP 传输/认证版本、标准来源解析与下载工具的具体实现。这些调查不得以悄悄降低功能或交付门槛解决失败。

参考：[Vercel Skills](https://github.com/vercel-labs/skills) 的标准 Skill 来源与项目/全局安装概念；[MCP](https://modelcontextprotocol.io/) 的连接与工具模型。Nema 的安装范围和权限由本设计定义，不直接接管其他客户端。
