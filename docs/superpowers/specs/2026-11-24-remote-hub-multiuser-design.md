## 如何服务 #45

#45 的判断标准要求：让一群人和 agent 围绕同一个项目维持一份有证据、可追溯的共同理解。#163 已经把「谁」写进了数据模型（用户、成员、提及归属），但今天这份共同理解只能由一个人的一台机器生产和阅读——身份恒为 `usr_local`、daemon 恒为一个、hub 恒在回环。本项把 #163 的数据模型接到真实的人和真实的机器上：谁在看、谁在写、哪台机器替谁执行，全部成为可归属、可审计的事实，而不是继续靠「反正只有一个人」兜底。它不改变讨论→工作包→实现报告的产品流，只把这条流的参与者从单数变成复数；凭据不出各人本机、归属不靠推断这两条与 #45 护栏一致（见「安全不变量」）。

## 现状核实（已核对，细节见 grounding 笔记）

1. **单 daemon 连接模型**。`apps/hub/src/daemonSocket.ts:73` 只有一个 `current` 连接，派发、RPC、通知全发它；第二个 daemon 的 hello（:410-431）会替换并关闭旧连接，并 `interruptRunning` 打断旧 daemon 在跑的任务（任务有回队重试，上限 3 次，`apps/hub/src/tasks.ts:148/158`——打断是真的，终局失败要等重试耗尽）。无注册、无心跳，`daemonId` 连接时现铸、断开即忘。
2. **无人身份执行面**。`apps/hub/src/identity.ts` 的 `localIdentity` 无条件返回 `usr_local`；桌面 gateway 身份校验的也只是「来自本机 gateway」，通过后仍是 `usr_local`。全仓生产代码没有创建用户的路径（唯一的 `insert into users` 是快照导入时种 `usr_local`），迁移 022 只种这一行；`apps/web` 没有登录页面。结果：第二个真人用户既不能被创建、不能登录，也加不进花名册（`addMember` 对未知用户 404）。
3. **内容 API 不查成员资格**。`requireMember`（`apps/hub/src/members.ts:28`）只在 `memberRoutes.ts` 被调用（花名册自身与 `/me`）；`uiApi.ts` 的话题/消息/条目、components、分享管理都不查。今天安全只因身份恒为全工作区的 owner；身份一旦可变，这里就是越权面。
4. **hub 暴露被政策锁回环，daemon token 无注册/吊销**。`apps/hub/src/app.ts:54` 的 `hostGuard` 只接受回环 Host（防 DNS rebinding），覆盖全部 hub 路由；SECURITY.md 第 31、47 行与报告范围（第 15 行起）把「在回环之外可达」定为不支持用法乃至报告事项。daemon 侧：全体 daemon 共用一个文件里的 token（`apps/hub/src/main.ts:22` 的 `ensureDaemonToken`），hello 时明文比较（`daemonSocket.ts:391`），没有每-daemon 凭据、注册表或单独吊销；另有为同机配套设计的版本全等校验（:396）。
5. **跨机器身份不一致**。仓库绑定键是 daemon 本机的 `git_common_dir` 路径指纹（唯一约束，迁移 005；`apps/hub/src/repos.ts:42/318`），两人绑同一远程仓库得到两条记录；`claimNextTask`（`apps/hub/src/tasks.ts:87`）挑最老的 queued 任务，`daemon_id` 只写入不参与挑选，不看哪个 daemon 持有该工作区的仓库或任务要用的账号。知识仓库与附件在 hub 的 dataDir、hub 的 EventBus 与连接表都在进程内存里——数据库（PostgreSQL 形态）不是远程化的障碍，文件型状态与单进程假设才是部署形态要交代清楚的部分。

## 设计

### 远程 hub 拓扑

一期只支持一种新拓扑，与既有两种形态并存、互不改变：

- **独立 hub（远程形态）**：`apps/hub` 以 `NEMA_DATABASE_URL` 连真实 PostgreSQL，部署在一台常开主机上；web 仍由 hub 同源提供（沿用现有 web 构建产物与 gateway 代理思路，但远程形态下浏览器直连 hub 的 web 入口，不再经某台桌面机的 gateway）。hub 保持单进程（EventBus 与连接表仍在内存）——一期明确不支持 hub 多副本，这不是缺陷而是范围声明。
- **daemon 在各人机器上**：每人的 daemon 以自己的凭据连入（下节），任务仍在本机执行、模型凭据仍只在本机（不变量）。daemon 客户端的 `--hub` 今天已能机械地指向 `wss` 远程地址，缺的是凭据分发与 hub 侧守卫，不是寻址能力。
- **文件型状态留在 hub 主机**：知识 git 仓库、附件、种子数据继续在 hub 的 dataDir——它们本来就归 hub 进程管辖，远程化不搬动它们。要消除的是「daemon 与 hub 共享同一文件系统」的假设：daemon token 不再靠共享文件分发（改注册流程），隔离目录清理明确归 daemon 本机（`nemaHome` 约定从「同机 Compose 特例」推广为「daemon 的文件系统永远归 daemon 自己清理」）。
- **既有形态不变**：桌面/npm 单机形态继续用 `localIdentity` 与 gateway 身份，行为与今天逐字节一致；Compose 同机形态可继续用共享文件 token 或迁移到注册凭据（D-5）。远程形态是一个新的 `IdentityProvider` 实现 + 新的 daemon 凭据校验，不是替换既有路径。

### daemon 注册、吊销与令牌生命周期

- **注册表**：新迁移建 `daemons` 表：`id`（稳定，替代现铸的临时 `daemonId`）、`owner_user_id`（所属用户，见 D-5）、`label`（用户可读名，如「我的 Mac mini」）、`credential_hash`（只存哈希，沿用分享 token 的存储先例）、`created_at`、`last_seen_at`、`revoked_at`。
- **注册流程**：用户在 hub 的设置页（登录态）生成一次性注册码（短时有效、单次使用）；在本机执行 `nema daemon register --hub <url>` 输入注册码，daemon 得到自己的长期凭据，存入本机既有凭据存储位置（0600 文件，与今天 token 文件同级保护）。hub 侧从此能区分「谁的哪台机器」。
- **连接校验**：hello 改为出示本 daemon 的凭据，hub 按 `daemons` 表查哈希比对；`revoked_at` 非空或查无此 daemon 一律拒绝并给出可读原因。版本校验按 D-9 改为最低兼容版本 + 能力协商。
- **多连接**：`current` 单例改为按 daemon 的连接表；派发与 RPC 按 D-6 的路由规则选连接。某个 daemon 断开只影响它自己的在跑任务（沿用回队机制），不再波及其他 daemon。
- **吊销与轮换**：用户（或 hub 管理员）可在设置页吊销任意一台自己名下的 daemon：吊销即断开其连接、其凭据立即失效、在跑任务按回队处理。凭据轮换 = 吊销 + 重新注册，不做原地换钥（简单且审计清楚，`member_events` 之外另有 daemon 事件记录：注册、吊销、连接拒绝各记一条）。

### 真人身份执行面

- **账号**：新迁移给 `users` 加凭据列或建 `user_credentials` 表（密码哈希，算法与参数见 D-3）与 `sessions` 表（会话只存 token 哈希、过期时间、创建时间，可整表吊销）。`usr_local` 保留为单机形态的合成身份，**在远程形态下不可登录、不出现在花名册候选里**（D-10）。
- **第一个账号（引导）**：远程形态的 hub 在「无任何真人账号」时进入引导状态：只允许回环或部署者持有的一次性引导令牌创建第一个管理员账号（令牌由 hub 启动时打印到控制台/写入 dataDir 的引导文件，与 daemon token 今天的分发方式同级）。引导完成后引导通道关闭。
- **建号与邀请**：后续账号只走邀请（D-4）：管理员或工作区 owner 生成邀请（一次性、带过期），被邀者凭邀请设显示名与密码完成建号。建号成功即是一个可被 `addMember` 引用的真实用户——#163 花名册的 404 死结由邀请流程在前面解决，花名册本身不改语义。
- **登录与会话**：web 新增登录页（`apps/web` 的 login 路由）与会话 cookie（httpOnly、Secure 在 TLS 下、SameSite=Lax）；`IdentityProvider` 的远程实现按会话解析出真实 `userId`，解析失败 401。登录接口限速与失败锁定按 D-8。登出 = 吊销当前会话；管理员可吊销某用户的全部会话（与移除成员是两个动作：前者断登录，后者断工作区资格）。
- **成员加入流程**：与今天一致的两步——先有账号（邀请建号），再由 owner 用既有 `addMember` 加入工作区；邀请可预带目标工作区，建号后由 owner 一键确认加入（仍走 `addMember` 的校验与 `member_events` 审计，不新开后门）。

### 内容 API 成员资格校验

- 所有按工作区作用域的内容路由（`uiApi.ts` 的话题/消息/条目、工作区设置、components 的工作区级操作、分享管理）在远程身份下统一前置 `requireMember`（管理类操作前置 owner 版）。这是把 #163 已经写好的判定铺到它本该覆盖的面，不是新判定逻辑。
- 落地顺序上有硬约束：**成员校验必须与真实身份同批上线**。只上身份不上校验 = 有名义账号但人人仍是事实 owner（比今天更危险，因为看起来像已授权）；只上校验不上身份 = 所有人被 `usr_local` 之外的路径误伤。单机形态下校验自动短路（`usr_local` 是全部工作区的 owner，与今天行为一致），这一点要有自动化测试钉住，防止远程工作误伤单机形态。
- `/room/*` 的每任务 run token、`/report` 的 report token 通道不在本节范围：它们是任务作用域的既有凭据，继续按现状校验；但 run token 的签发从此发生在「已按 D-6 路由选定的 daemon」前提下，不再是任意连接可领。

### 认证先于远程暴露的落地顺序

实现顺序即安全顺序，写死在实施计划里、不可调换：

1. **政策先行**：修订 SECURITY.md 第 31、47 行与报告范围的口径——把「回环之外可达」从一律不支持，改为「仅在远程形态下、且真实认证与 Host 清单同时启用时受支持」；同时补远程形态的威胁模型（明文、窃听、爆破面）。这一步只改文档，不改任何绑定行为。
2. **身份与校验**：真人身份执行面 + 内容 API 成员校验 + daemon 注册/吊销，在 hub 仍只绑回环时全部落地并通过验收（此时远程形态可在回环上完整演练）。
3. **连接多路化**：`current` 改连接表与 D-6 路由，仍在回环下验收多 daemon 场景。
4. **最后放开暴露**：新增「允许 Host 清单」配置（部署者显式列出 hub 的对外主机名/IP），`hostGuard` 改为「回环恒允许 + 清单内 Host 在远程形态下允许」；绑定地址放开为部署者显式配置。默认配置下行为与今天完全一致（不填清单 = 只有回环）。TLS 按 D-8 由部署通道解决，hub 本体不终止 TLS。

## 安全不变量

- **凭据不出 daemon 本机**（现行不变量，继续成立）：模型账号、MCP secret、GitHub 令牌只存在各人 daemon 本机；hub 与任务只传 ID（accountId 等），新设计不得把任何人的模型凭据集中到 hub。任务记录新增的是「哪个用户、哪台 daemon」的归属，不是凭据。
- **hub 只存哈希**：用户密码、会话 token、daemon 凭据、邀请码在 hub 侧一律只存哈希（沿用分享 token 与 report token 的既有先例）。
- **默认不暴露**：不配置远程形态时，hub 的绑定、Host 守卫、身份行为与今天逐字节一致；远程形态必须由部署者显式开启并完成引导，升级既有安装不会自动打开任何远程面。
- **归属可审计**：成员变更沿用 `member_events`；新增账号创建、邀请、daemon 注册/吊销、登录失败锁定各留事件。消息与任务的作者/执行归属只来自已认证身份，不由客户端自报。
- **最后一个 owner 保护**等 #163 既有不变量在远程形态下继续成立，且对「移除成员」与「吊销会话/daemon」分别生效，不互相替代。

## 分期建议

- **一期 = v0.3.3（本文范围）**：上述设计全部——政策修订、真人身份执行面（引导/邀请/登录/会话）、内容 API 成员校验、daemon 注册表与每机凭据、多 daemon 连接与最小路由、Host 清单放开。部署口径：独立 hub + PostgreSQL，跑在部署者控制的主机上，经受信网络（局域网或自备 VPN/组网）访问；hub 不直接面对公网。
- **二期（未排期，本文只登记）**：repo 绑定键从本机路径指纹迁到远程仓库标识（D-7 的后半）、任务路由增强（daemon 上报账号可用性与负载、用户可指定执行 daemon）、统一审计面（跨成员/daemon/登录的「谁做了什么」查询）。
- **三期方向（不排期、不承诺）**：公网直连形态（hub 内置或托管 TLS、OIDC/外部 IdP 登录）、托管版 hub（若 #167 待定问题 3 的答案最终是「不想自己部署」占主导，这期才是对症的）。

## 验收口径

三类证据分开写，不互相替代：

- **静态检查**：根 `npm run typecheck` 与 `npm run typecheck -w apps/cli` 通过；web 改动另加 `npm run lint -w apps/web` 与 `npm run build -w apps/web`（登录页）。新迁移在迁移清单与两驱动的迁移测试中出现。
- **自动化测试**（hub 集成与单元）：① 双 daemon 同连不互踢，各自在跑任务不被对方 hello 打断；② daemon 凭据吊销后连接被拒、在跑任务回队；③ 非成员读/写内容 API 得 403、成员正常、owner 操作限 owner；④ 邀请全流程（生成→建号→`addMember` 成功）与过期/复用邀请被拒；⑤ 引导通道在首个账号建立后关闭；⑥ 单机形态回归：`usr_local` 路径行为与今天一致（成员校验短路）；⑦ Host 清单外的主机名在远程形态下仍 403（rebinding 防护不回归）。迁移在 PGlite 与真实 PostgreSQL 两驱动上各跑一遍。
- **真实环境验收**：按 2026-11-16 测试政策在 VM 内走 Compose 路线演练远程形态：独立 hub（PostgreSQL）+ 两个 daemon 进程（不同数据目录、不同凭据）+ 两个真人账号，完整走一遍「邀请建号→加入工作区→甲发任务由甲的 daemon 执行→乙可见并回复→吊销乙的 daemon 后其连接被拒」。桌面实机不主动测；公网暴露不在验收范围（一期口径是受信网络）。

## D 项（已定案：2026-11-24 维护者批准，全部按推荐）

- **D-1 互享对象与 hub 定位**：共享哪几样、hub 属于谁？**推荐：小团队共用一个 hub（单 hub、多用户、非多租户）；互享对象 = 工作区内的知识、聊天与任务（即 #163 花名册圈定的全部内容），仓库绑定与模型账号是各 daemon 的本机执行资源，不算共享对象、只共享「持有状态」。** 理由：#167 的目标是让一群协作者围绕同一批工作区协作，花名册已经是现成的共享边界；多租户/托管是另一个产品（见 D-2 与三期方向），没有证据表明当前瓶颈在那里。备选：(a) 一人一个 hub + 跨 hub 分享——等于把 #165 的链接模型做成双向，身份问题绕不过去且同步语义全新，代价是再造一套协议；(b) 多租户托管——运维与隔离面最大，且 #167 待定问题 3（瓶颈是「看不到」还是「不想部署」）尚无答案，先做它等于赌方向。
- **D-2 一期暴露面**：一期做到公网直连，还是只到受信网络？**推荐：只到受信网络（局域网 / 自备 VPN 组网），hub 不内置 TLS 终止、不做公网形态。** 理由：一期的核心风险在身份与授权的正确性，不在传输层；把 TLS/证书/公网爆破面同时引入会让验收面翻倍。受信网络是小团队今天就有的现成条件（本团队已在用组网工具）。备选：一期即公网 + 反代/TLS——部署灵活，但 SECURITY.md 威胁模型、登录防爆破、证书运维全要同期定案，v0.3.3 体量失控；且一旦口径写成「支持公网」，后续收紧即是兼容性事件。
- **D-3 人类凭据形态**：密码、OIDC 还是无密码链接？**推荐：本地账号密码（argon2id 哈希）+ 服务端会话（token 只存哈希、httpOnly cookie）。** 理由：小团队自部署场景里密码是唯一不依赖外部服务的形态；会话表可吊销、可审计，与 daemon 凭据的生命周期管理同构。备选：(a) OIDC/外部 IdP——团队若已有 IdP 更省心，但把「能不能登录」绑定到外部可用性，且每个自部署者都要先有 IdP，门槛倒置；留三期。(b) 邮箱 magic link——仓库没有邮件发送通道，先要再引入一个外部依赖与送达性问题。
- **D-4 建号与加入流程**：开放注册、管理员建号还是邀请制？**推荐：邀请制——管理员或工作区 owner 发一次性邀请（带过期），被邀者设名与密码完成建号；第一个账号走一次性引导通道。** 理由：邀请把「谁能有账号」的决定权留给已在系统里的人，与花名册的 owner 判定同源；同时解决了 `addMember` 对未知用户 404 的死结（先有账号、再谈成员）。备选：(a) 管理员后台直接建号发初始密码——初始密码的分发与强制改密流程都要另设，且密码经人手传递；(b) 开放注册——与 D-2 的受信网络口径冲突，公网下更是直接的爆破与灌水面。
- **D-5 daemon 身份绑定**：绑人、绑机器还是绑一对？**推荐：绑「用户 + 机器」一对——每 daemon 一份独立凭据，登记在某个用户名下（`daemons.owner_user_id`），注册码由该用户在登录态生成；同人多机各一份凭据、可单独吊销。** 理由：任务归属要同时回答「谁的任务」与「哪台机器跑的」；人走时吊销其名下全部 daemon、机器丢时只吊销一台，两种语义都干净。既有单机/Compose 形态的共享文件 token 保留不动（本机配套口径），远程形态禁用共享 token。备选：(a) 只绑机器（hub 管理员发凭据）——机器换人时归属错误，且与成员资格脱钩，路由时还要再查一层；(b) 只绑人（人级 token 多机共用）——退化成今天的共享 token 问题（一机泄露全机队受影响、无法单独吊销）。
- **D-6 多 daemon 任务路由**：任务派给谁？**推荐：一期最小可解释规则——任务只能派给同时满足三条的在线 daemon：① 其所有者是该工作区的未移除成员；② 它上报持有该工作区的绑定仓库（工作区未绑仓库则此条 vacuous）；③ 同一工作区同时只跑一个任务（既有不变式不变）。无合格 daemon 时任务留在队列，UI 显示「在等哪台 daemon」的原因（无人在线 / 在线者未持有仓库）。账号仍在 daemon 本机按既有 accountId 解析，选不到账号按今天的失败路径呈现。** 理由：规则每条都对应一个真实约束（资格、仓库在不在、凭据在不在），且可向用户解释；先把「不派错」做对，「派得最优」留二期。备选：(a) 用户发任务时手动指定 daemon——把调度知识推给用户，多人场景下心智负担大，且指定者未必知道各机持有情况；可作为二期的覆盖选项。(b) 沿用今天「随便派、失败再说」——任务会系统性落到没有仓库/账号的机器上失败回队，多人下等于不可用。
- **D-7 repo 绑定身份**：一期迁不迁绑定键？**推荐：一期不迁键。`git_common_dir` 继续作本机绑定键；hub 侧利用已存的 `remote_url` 做规范化后仅用于「同一远程仓库」的提示与 D-6 路由的持有匹配（daemon 上报自己持有哪些绑定，hub 按工作区绑定关系核对）。绑定键迁移单独立项进二期。** 理由：迁键牵动 `repos.sync`、`main_moves`、`repo_hooks` 一整套（#167 原文第 4 条），且存量用户要不要重新绑定是独立的产品决定；它阻塞的只是「两人绑同一仓库自动合并成一条」，不阻塞身份与多 daemon 主线。备选：一期迁键——身份主线被仓库子系统绑架，v0.3.3 的验收面与回滚成本都不可控。
- **D-8 暴露与传输安全**：放开绑定时配套什么？**推荐：三件套——① Host 改为部署者显式配置的允许清单（回环恒允许，清单外一律 403，保留 rebinding 防护语义）；② 登录接口限速 + 连续失败锁定，写进验收；③ TLS 由部署通道承担（受信网络/VPN 或部署者自己的反代），hub 不内置证书管理，但远程形态下会话 cookie 强制 Secure 的前提写进部署文档（即远程形态事实上要求 https 或组网加密层）。** 理由：hostGuard 的防护目标是 rebinding 不是「回环」本身，清单制保留了防护又给了远程形态合法的主机名；TLS 终止的证书生命周期是独立运维面，不该塞进 hub。备选：(a) hub 内置 TLS + ACME——证书签发/续期/私钥存储全要自理，且与 D-2 的「不做公网形态」自相矛盾；(b) 只靠认证、Host 全放开——rebinding 攻击面原样回来，SECURITY.md 的既有防线被拆掉。
- **D-9 daemon 版本策略**：hello 的版本全等校验怎么办？**推荐：改为 hub 声明最低兼容版本 + 已有 features 能力协商：低于最低线拒绝并给出升级原因，高于或等于即放行（协议不兼容靠 features 缺失显式报错，不靠版本号猜）。** 理由：多机队不可能全队同刻升级，全等校验在远程形态下等于「升级 hub 即全队停机」；最低线 + 能力协商是既有 hello 字段（version、features）就能承载的最小改动。备选：(a) 维持全等——只适用于同机配套安装，远程形态直接不可用；(b) 完全不查——协议漂移时无声失败，排障成本后置且更高。
- **D-10 单机形态的兼容**：`usr_local` 在新体系里是什么？**推荐：单机形态（桌面/npm 本地、Compose 同机）行为完全不变，`localIdentity` 与 gateway 身份不动；`usr_local` 只作为单机形态的合成身份存在，远程形态下不可登录、不进花名册候选、其历史内容归属保持原样显示。** 理由：#163 的验收口径之一是单用户无感，远程化不该让存量单机用户被迫建号或看到任何变化；两种形态共用同一套数据模型、只换 IdentityProvider 实现，正是 #163 留缝的目的。备选：统一账号体系（单机也要登录）——破坏全部存量体验与既有验收，且把本项的回归面扩到每个现有用户。

## 不在范围

- hub 多副本/高可用（进程内 EventBus 与连接表的跨进程化）——一期明确单进程，二期也不预设。
- 托管版 hub 与多租户隔离——三期方向，取决于 #167 待定问题 3 的后续证据。
- 模型账号在多人间的共享、代付或额度分摊策略——凭据不出本机是不变量，本项只做归属记录，不做账号共享。
- #165 只读分享机制的任何改动；分享 token 不复用为登录或 daemon 凭据（威胁模型不同）。
- 桌面实机验收——按 2026-11-16 测试政策不主动做，真实环境验收走 VM 内 Compose 路线。
