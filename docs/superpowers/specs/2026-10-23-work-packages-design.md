# 开发包：Nema 写 spec 和 plan，交给 coding agent

日期：2026-10-23。上游设计：`docs/superpowers/specs/2026-10-21-nema-room-design.md`（主 spec）、`docs/superpowers/specs/2026-10-23-codebase-and-plugins-design.md`（代码库与插件，以下称代码库 spec）。

标注：【决定】是用户定下的；【Claude 的决定】是 Claude 按自己对产品的理解定的——用户在 2026-10-23 要求「直接按最直观的产品理解来做这个设计」，所以本文大部分细节是 Claude 的决定，用户审阅时可以逐条推翻。

## 意图

Nema 已经把零散的记录整理成需求、决策、取舍和待确认，也能读懂代码、接收 coding agent 的上报。缺的是中间一步：**把「要做什么、为什么」变成 coding agent 能直接执行的东西**。

现在这一步靠用户自己：翻知识、凑上下文、写任务说明、交给 coding agent。这正是信息丢失、需求漂移的地方。【决定：第二阶段让 Nema 写 spec 和 plan，交给 coding agent 实现，Nema 不实机去做】

做法沿用 superpowers 的方法【决定】：先把设计写清楚（spec），再拆成可测试的小任务（plan），每个任务带测试步骤；coding agent 照 plan 做，做完上报；Nema 用代码库 spec 的上报与核实闭环判断做完没有。

一句话：**开发包 = 一份 spec + 一份 plan + 它们对应的需求，Nema 写，用户批，coding agent 做，Nema 核实。**

## 目标

- 用户在聊天里说「把 R-3、R-5 做成开发包」，或在需求条目上点「生成开发包」，Nema 产出一份开发包草稿。
- 写之前先追问（grill）：相关的待确认、`inferred` 条目、冲突的决策，影响实现的先问清楚。
- spec 里每个说法都能追到知识条目；推断出来的内容明确标出。
- plan 以真实代码为准：引用的文件、函数用代码库函数核对过；不存在的标为「新建」。
- plan 的每个任务写明它满足哪些需求，coding agent 上报时引用「W-2 任务 3」，Nema 据此逐任务核实。
- 用户审阅、修改、批准；批准前 coding agent 拿不到。
- coding agent 一条命令拿到开发包，自己写进它的工作目录。
- 开发包有状态：草稿 → 已批准 → 进行中 → 已完成，进度来自上报核实，不靠谁说一句「做完了」。

## 非目标

- Nema 自己写代码、跑测试、开 PR。
- Nema 往用户仓库里写文件（代码库 spec 的反目标）。交接由 coding agent 在它自己的工作区里完成。
- 自动把开发包派给 coding agent（像 Multica 那样排队执行）。以后再说。
- 开发包之间的依赖图、排期、估时、分工（主 spec 非目标：不做进度管理）。
- 在 Nema 的 Agent 里直接运行 superpowers 技能本身（它们假设有文件系统和 shell，Nema 的 Agent 没有）。

## 反目标

- spec 里出现知识库里没有、又没标为推断的「决定」。
- plan 引用了仓库里不存在的文件或函数，却没标「新建」。
- 开发包和已定决策矛盾而没有指出。
- 开发包在用户批准前就被 coding agent 拿走执行。
- 状态显示「已完成」，但对应任务没有核实通过的上报（或用户确认）。
- 追问变成刁难：问了不影响实现的问题，或者一次问一串。

## 已有决定（沿用）

- Agent 只走 Room（主 spec 6.2、代码库 spec 决定 2）。开发包也是通过新的 Room 函数写入的知识。
- 每次运行无状态，同一 workspace 串行（主 spec 4.5）。
- 依据 `stated / decided / inferred`、进库与确认时间（主 spec 4.3、4.4）。
- 上报、三级实现状态、「做完了 = 已合入远端主分支并核实」（代码库 spec 决定 5）。
- grill-me 一次只问一个问题；冲突先追问（主 spec 4.3）。

## 设计

### 1. 开发包是知识的一种【Claude 的决定】

- 新条目类型 `workpackage`，编号前缀 `W`，目录 `workpackages/`。每个开发包是一个目录：`workpackages/W-2/entry.md`（标题、状态、关联需求、frontmatter）、`spec.md`、`plan.md`。
- 存进 workspace 的知识仓库，和其他知识一样每次修改一个 commit、有历史和 blame；团队只读时也能看到（属于「项目知识」，不是原始聊天）。
- frontmatter：`requirements`（覆盖的需求编号）、`repos`（涉及的绑定仓库）、`status`（`draft` / `approved` / `in_progress` / `done` / `dropped`）、`approvedAt`、`approvedVersion`（批准时的 commit）、`basis`（沿用依据字段，整份开发包取最弱的那一级）。

### 2. 生成流程

一次「生成开发包」是一个系统发起的任务（代码库 spec 决定 8 的 `system` 消息），分三步，都在同一次 Agent 运行里：

**第一步：就绪检查（grill）**【Claude 的决定】

- Agent 读取相关需求、它们关联的决策和取舍、相关的待确认，以及被标 `inferred` 的内容。
- 找出**会改变实现**的不确定点：没定的取值（「多快算快」）、互相冲突的决策、没有依据的推断、缺失的验收标准。
- 有这类问题时：每个问题建一条待确认，聊天里只问优先级最高的一个（沿用 4.3），本次**不写 spec**，开发包停在「待澄清」（`draft`，并标注卡在哪个问题上）。用户回答后，Nema 自动重试生成。
- 没有这类问题，或只剩不影响实现的小问题：继续写。小问题写进 spec 的「留给实现者」。
- 严格程度是 workspace 设置（见第 6 节 grill-me 插件）。

**第二步：写 spec**

结构沿用 superpowers 的设计文档【决定：沿用 superpowers 方法；结构为 Claude 的决定】：

- 意图与原因（为什么做，引用需求和来源消息）
- 目标、非目标、反目标
- 约束（引用决策、取舍）
- 已定的做法（每条后面标来源条目编号，例如 `[D-12]`；推断的标 `[推断]`）
- 留给实现者的部分
- 验收标准（每条需求一组，可检验的说法）

规则：没有来源条目、又不是标明的推断的句子，不能写进「已定的做法」。hub 在保存时检查：「已定的做法」一节里每个列表项至少有一个 `[X-n]` 或 `[推断]` 标记，否则拒绝保存并把缺标记的行返回给 Agent。

**第三步：写 plan**

结构沿用 superpowers 的实现计划【决定：沿用 superpowers 方法；结构为 Claude 的决定】：

- 头部：目标、架构、技术栈、对应 spec、全局约束、Review Focus。
- 任务列表：每个任务有「文件」（新建 / 修改，带仓库）、「接口」（消费 / 产出）、测试步骤（测试名与断言）、实现步骤、验证命令、提交信息，以及**满足的需求**（例如 `满足：R-3、R-5`）。
- Agent 用代码库函数核对：plan 里「修改」的每个文件必须在对应仓库主分支上存在；hub 保存时再用 `code__read` 的同一套检查确认一遍，不存在的路径拒绝保存（除非标为「新建」）。
- 任务数上限 15。超过时说明拆分，建议拆成多个开发包。【Claude 的决定】

**运行上限**：生成开发包的任务比普通整理大，单独给上限：48 轮模型调用、120 次工具调用、20 分钟。其余运行仍是 24 / 60 / 10 分钟。【Claude 的决定：需要同步修改 runtime spec 的上限说明】

### 3. 审阅与批准

- 右侧项目知识新增「开发包」分组，按状态排序（待澄清、草稿置顶）。
- 打开开发包：三个标签页——概览（状态、覆盖的需求、各任务进度）、Spec、Plan。Spec 和 Plan 以 Markdown 渲染，来源标记 `[D-12]` 可点击跳到条目。
- 用户修改有两种方式：
  - 在聊天里说「W-2 的任务 3 拆成两个」，Nema 跑一次修订任务，生成新版本；
  - 直接编辑 Markdown（和编辑条目一样，作为 `user` 提交）。
- 每次修改都是一个 commit；历史标签页沿用条目的版本与差异视图。
- **批准**：开发包上的「批准」按钮。记录批准时的 commit。批准后再修改，状态退回 `draft`，需要重新批准。【Claude 的决定：避免 coding agent 拿到的和用户批的不是同一份】
- 批准与否只由用户决定，Agent 不能把开发包设为 `approved`（Room API 强制）。

### 4. 交接给 coding agent【Claude 的决定】

Nema 不写用户仓库，所以由 coding agent 自己拿：

- 命令：`nema wp get W-2 [--dir <目录>]`。在仓库目录里执行，按代码库 spec 的路由规则（共享 git 目录）找到 workspace；只能取**已批准**、且 `repos` 包含当前仓库的开发包。默认写到 `<当前目录>/.nema/W-2/spec.md`、`plan.md`（目录不存在则创建；文件已存在且内容不同则拒绝覆盖，除非 `--force`）。也可以 `--stdout` 只打印。
- 写进去的 plan 头部加一段固定说明：做完每个任务后用 `nema report --entries W-2 --task <n> ...` 上报。
- 代码库 spec 的 `nema report` 技能更新：发现工作目录里有 `.nema/W-*/plan.md` 时，按其中的任务编号上报。
- `nema wp list` 列出当前仓库可取的已批准开发包。
- 鉴权沿用代码库 spec 的上报令牌（本机），不新增凭证。

### 5. 进度：逐任务核实

- `nema report` 增加可选字段 `task`（开发包任务编号）。`entries` 里带 `W-2` 时，hub 把这次上报关联到该开发包的任务。
- 任务状态与需求的实现状态同一套：已上报 → 已核实 / 有出入；核实规则完全沿用代码库 spec 决定 5（提交存在、已合入远端主分支、声称改了的文件确实改了）。另外检查：任务「文件」里列为修改或新建的路径，至少有一个出现在提交的改动里；一个都没有算「有出入」。
- 开发包状态由任务状态推出，不由 Agent 设置：
  - 第一个任务被上报 → `in_progress`
  - 所有任务已核实 → `done`，并把覆盖的需求的实现状态更新为 `verified`（证据引用各任务的上报）
- 没有上报时的兜底沿用代码库 spec：Nema 从代码推断的完成只到「已上报（代码推断）」，任务要升为已核实，需要用户在任务上点确认。

### 6. 两个自带插件：superpowers 与 grill-me【决定：作为自带插件；细节为 Claude 的决定】

两者都是 `local`、在 hub 侧运行（不经 daemon），默认开启，可在 workspace 的「代码与插件」页开关。

**superpowers（写 spec / plan 的方法）**

- 提供的不是工具调用，而是**写作规则和模板**：spec 与 plan 的结构、每节要写什么、什么算合格（例如「每个测试步骤要有测试名和断言」「不要写 TBD」）。来源是 superpowers 的 brainstorming / writing-plans 技能，按其 MIT 许可改写为 Nema 的规则文本，放在仓库 `vendor/superpowers-rules/`，注明来源版本。
- 提供 Room 函数：`workpackage__save_spec`、`workpackage__save_plan`、`workpackage__read`（读已有开发包）。保存时执行第 2 节的检查（来源标记、文件存在、任务数）。
- 关闭时：Nema 不提供「生成开发包」。

**grill-me（追问）**

- 把主 spec 4.3 的追问规则从写死的 prompt 变成插件，可配置：
  - 严格程度：`严格`（任何影响实现的问题都先问，默认）/ `宽松`（只在决策冲突时停下，其余写进 spec 的「待确认」小节）。
  - 补充规则：workspace 可以加一段自己的追问要求（纯文本，最多 2000 字），附加在内置规则之后；不能删改内置规则。
- 对日常整理任务和开发包生成都生效。
- 关闭 grill-me 时：日常整理仍然「不确定就进待确认」（这是主 spec 4.3 的底线，不可关），只是不在聊天里主动追问；开发包生成跳过就绪检查，但所有不确定点仍写进 spec 的「待确认」小节。

### 7. 界面要点【Claude 的决定】

- 需求条目上：「生成开发包」按钮（可多选需求后生成一个）。
- 聊天里：生成任务的结果显示为一张卡片——开发包编号、状态、覆盖的需求、追问（如果卡住）。
- 开发包详情：概览 / Spec / Plan / 历史 四个标签页；「批准」「重新生成」按钮；概览里每个任务一行，显示状态标签（沿用实现状态的样式）和对应上报。
- 文案 ja / en / zh。样式沿用主 spec 4.6。

## 留给实现者

- 开发包目录在知识仓库里的具体文件命名、frontmatter 字段的磁盘写法。
- hub 对 spec「已定的做法」一节与 plan「文件」一节的解析方式（只要能做第 2 节的检查）。
- superpowers 规则文本的具体措辞（保持原方法的要点）。
- `nema wp get` 的输出格式细节。

## 实现前必须核对

- superpowers 的许可证与改写方式（保留版权声明）。
- 生成开发包的运行上限放大后，Codex 直连与 Claude Code 两种运行方式都能在 20 分钟内完成一个中等规模的开发包（用假模型测上限逻辑；真机冒烟由用户执行）。

## 验证

- 单元测试不调用真实模型：用假的 Responses 服务和假的 `claude` 脚本，按固定脚本调用 `workpackage__*` 函数。
- 就绪检查：存在影响实现的待确认时不写 spec，开发包停在待澄清并只追问一个问题；回答后自动重试。
- spec 保存：「已定的做法」里缺来源标记的行被拒绝并返回给 Agent。
- plan 保存：「修改」不存在的文件被拒绝；标「新建」的放行；超过 15 个任务被拒绝。
- 批准：Agent 不能批准；批准后修改退回草稿。
- 交接：未批准、或不涉及当前仓库的开发包取不到；已存在且不同的文件不被覆盖。
- 进度：任务上报核实通过 → 任务已核实；全部核实 → 开发包已完成、需求升为已核实；代码推断的任务需要用户确认。
- grill-me 宽松模式下只在决策冲突时停下。
- 真机冒烟（用户执行）：选两条需求生成开发包 → 回答一个追问 → 批准 → 在 Claude Code 里 `nema wp get` 并按 plan 做第一个任务 → 上报 → 任务显示已核实。
