# 提及候选搜索的合成基准

这是 [设计规格](2026-11-07-mention-candidate-search-design.md) 的实验记录。数据是脚本生成的，库名是 `nema_mention_bench`，跑完删除。不读 `NEMA_DATABASE_URL`，不使用应用库 `nema`，不使用真实工作区。

复跑：

```bash
node scripts/bench/mention-candidate-search.mjs --out /tmp/mention-bench.json
```

`pg` 来自仓库依赖（`apps/hub` 的 `pg`）。脚本默认连接 `127.0.0.1:5433` 的维护库 `postgres`，主机不是本机就拒绝。可用 `NEMA_BENCH_ADMIN_URL` 覆盖，但数据库名必须是 `postgres`。`--runs` 默认 5，`--scales` 默认 `500,2000,10000`。

## 规模和分布

500 等于现在的条目和话题池，池外目标此时还在池内。2000 是这个池的 4 倍。10000 是 20 倍，足够让顺序扫描扫过该 workspace 的每一行，同时仍是一个合成项目，不是容量规划。没有继续加到更大，因为 10000 已经显示扫描行数等于表的行数；更大只会把同一种扫描放大，而这台机器上的放大倍数不能写成生产承诺。

每个规模 N：`D-1` 最新，`D-N` 最旧。标题按 `i` 分配：`i = N` 为 `最旧独特标题`，`i = N-1` 为 `甲发中流乙`，`i = N-2` 为 `发布`，`i % 10 = 0` 为 `发布流程 i`，`i % 10 = 1` 为 `版本发布 i`，`i % 10 = 2` 为 `notes/发布/log-i`，`i % 17 = 0` 为 `罕见标记-i`，其余为 `记录 i 普通标题`。每个话题有一条回复。附件名复制标题。计时结束后才装入第二个同样大小的 workspace，避免它混进斜率。

10000 行的命中数：`发布` 字面和子序列都是 3000；`发流` 字面 0、子序列 1000；`甲流乙` 字面 0、子序列 1；`最旧独特标题` 各 1；`没有这个词zz` 各 0；`发` 字面和子序列都是 3001。

## 墙钟

中位毫秒。一次调用并行跑条目、话题、附件。现实现是现在的三条 SQL（条目和话题各 500、附件 51）加上进程里的 `fuzzyScore`。它没有调用 `mentionContext`，墙钟不含附件 `stat` 和 `missing` 更新；那些在附件一节。子串话题查询和另外两种一样 `left join messages`，按最后活动时间排序。它的谓词仍是字面子串，前缀档仍是标题前缀，不是 `fuzzyScore` 的段前缀。连接池设置了 `statement_timeout` 和 `idleTimeoutMillis: 0`，计时前预热 16 条连接。

`D-(N-1)` 是 `甲发中流乙`。N 为 500 时它仍在最新 500 条里，现实现和两种子序列都能返回它，子串不能。N 为 2000 和 10000 时，现实现和子串的菜单都没有它，正则和线性的菜单是 `D-1999` 或 `D-9999`。`最旧独特标题` 在 10000 行时同样：现实现菜单为空，另外三种返回 `D-10000`。

`发流` 在 2000 和 10000 行时，全表 `fuzzyScore` 的前 8 名是较新的 `发布流程` 行，所以现实现的条目菜单可以和全表一致，同时仍然看不到那条池外的 `甲发中流乙`。能不能找到池外目标，要看查询是不是把那一行排进前 8，而不是只看 `发流` 有没有任意命中。

正则和线性在三个规模、七个查询上，条目、话题、附件的前 8 名都和全表 `fuzzyScore` 相同。这次标题都在 BMP 内，SQL 用的是 `char_length`，JS 用的是 UTF-16 代码单元；非 BMP 的更短优先还没有测到。子串只在空查询、零命中和唯一标题上相同；`发布`、`发`、`发流`、`甲流乙` 不同。子串把 `发布流程` 当标题前缀、按时间排，全表打分则把 `notes/发布/log` 的段前缀放在更前。

## 查询计划

10000 行、只有一个 workspace 时，空查询的条目计划是 `Seq Scan`，实际扫 10000 行，滤掉 0 行。`LIMIT 500` 的执行时间 2.21 ms，`LIMIT 9` 是 2.06 ms。话题空查询两次都要分组全部话题，执行时间分别是 10.62 ms 和 9.60 ms。返回行数从 500 降到 9 没有拿掉这次扫描。

`发布` 的正则在加入第二个 10000 行 workspace 之后：扫到的命中仍是 3000，滤掉的行从 7000 变成 17000，`shared hit` 从 114 变成 227，`shared read` 仍是 0。返回的 9 行里 `workspace_id` 不属于 `bench-a` 的个数是 0。执行时间从加入前那次 explain 的 10.00 ms 变成 10.82 ms。这是各一次 explain，不是五次中位。正确性探针也对四种候选 SQL 投影了 `workspace_id`：查询 `最旧独特标题` 时，返回行里不属于 `bench-tiny` 的个数都是 0。

主键存在，这次优化器没有用它。

## 折叠、转义和重复串

小表探针，不是计时：

| 标题 | 查询 | JS | SQL `lower` 后的正则 | 两侧都 `lower` 的线性 |
| --- | --- | --- | --- | --- |
| `İstanbul` | `i` | 命中 | 命中 | 命中 |
| `İstanbul` | `İ` | 命中 | 不命中 | 命中 |
| `i` | `İ` | 不命中 | 不命中 | 命中 |
| `straße` | `ss` | 不命中 | 不命中 | 不命中 |
| `straße` | `ß` | 命中 | 命中 | 命中 |
| `a😀b` | `😀` | 命中 | 命中 | 命中 |
| `发` 与 `流` 之间有换行 | `发流` | 命中 | 命中 | 命中 |
| `AbCdef` | `abc` | 命中 | 命中 | 命中 |
| `a.b*c` | `.*` | 命中 | 命中 | 命中 |
| `abc` | `.*` | 不命中 | 不命中 | 不命中 |
| `100%_done` | `%` 或 `_` | 命中 | 命中 | 命中 |

JS `toLowerCase("İstanbul")` 得到 `i` 加组合点。SQL `lower` 得到 `istanbul`。正则模式用 JS 折叠、列用 SQL `lower`，所以查询 `İ` 漏掉 `İstanbul`。线性两侧都用 SQL `lower`，所以查询 `İ` 命中标题 `i`，JS 不命中。

`%`、`_`、`.*` 作为参数里的模式时，转义后不匹配全部行。子串找不到 `.*` 在 `a.b*c` 里的子序列。

另有 1000 行、每行标题是 500 个 `a`，语句超时 3 秒。查询 8 / 20 / 30 / 100 / 200 个 `a`：正则 4.64、5.88、7.46、30.49、109.25 ms；线性 17.79、38.65、56.26、178.36、359.68 ms。都返回 1000 行，都没有超时。没有把这个结果推广成「200 字以内的正则都安全」。

## 附件缺失和并发

40 个附件名都匹配，文件只从第 17 个起存在。`stat` 最新 16 个 id：20 次的中位 0.30 ms，存在 0、缺失 16。50 个真实临时文件：中位 0.71 ms。16 条 `missing` 更新包在事务里回滚，5 次的中位 2.04 ms（1.94–3.29）。更新提交前仍挂着 `attached` 的行是 24。菜单若停在第 16 次 `stat`，返回 0 个文件。这 16 次只覆盖最新的 16 个 id，不覆盖全部可用附件。

10000 行上连续查询 `发`、`发布`、`发布流`、`发布流程`：现实现串行中位 39.67 ms，四路同时在飞 18.14 ms；正则 52.39 / 35.31；子串 24.29 / 16.68。8 个客户端同时各跑一组 `发布`：现实现墙钟中位 32.08 ms（30.87–33.47），正则 80.67 ms（79.68–84.00）。这是连接池上的重叠，不是浏览器 debounce 的 150 ms，也没有测取消后的服务端浪费。

## 这些数字不是什么

不是菜单的响应时间上限，不是「不比现在慢」的验收结论，不是 P2-02 的基线。冷缓存、PGlite、更宽的字符集和更长的真实标题都没有出现在这次运行里。
