## 如何服务 #45

#45 的判断标准在启动入口上的要求是：打开共享房间要可靠、可感知，等待时间可控。本项不新增功能，只缩短**首次运行**在 Windows 上的冷启动 DB 等待——这是新用户第一次打开 Nema Room 时最长的一段静默等待。它不改变任何已启动用户的行为，也不放松私有文件校验与迁移完整性（见「安全不变量」）。

## 现状核实（已核对）

### 冷启动 DB 的代码路径

- 桌面 home 为 `~/.nema/desktop`（`apps/local/src/paths.ts` 的 `defaultHome()`），数据库目录是 `<home>/db`，hub 数据目录是 `<home>/data`，两者分开。
- `createLocalDb(dataDir)`（`apps/hub/src/db/pglite.ts`）：`new PGlite(dataDir)` 后调 `migrate(db)`；迁移失败则关闭并抛错。调用方只有两处：`apps/local/src/runtime.ts`（桌面/本地运行时）与 `apps/local/src/import.ts`（导入路径）。
- `migrate`（`apps/hub/src/db/db.ts`）：建 `schema_migrations` 表（若不存在），按文件名顺序逐个事务应用未执行的 `.sql`（当前 001–022 共 22 个），每个迁移连同记账插入同事务提交。
- 因此一次全新冷启动的 DB 成本 = 在空目录上初始化 PGlite 集群 + 顺序执行 22 个迁移事务。`startup-sample` 测的正是这段（`new PGlite` 就绪 + `migrate`）作为 `createLocalDb` 总时长的代理量。

### 预置能省什么、不能省什么

`startup-sample` 的冷/热口径：冷 = 全新目录（初始化 + 全部迁移），热 = 同一目录复用（集群已存在、迁移已应用）。#186 Task 3 的 windows 数字：冷中位 3484ms、热中位 443ms。也就是说冷开销里约 87% 是「从零建库」这一段——正是预置数据目录能跳过的部分；预置后的首次打开应落在「解开预置 + 打开既有集群」的量级，接近热口径再加一份解压/拷贝成本。预置**不能**省的是 PGlite 引擎本身的加载（WASM 初始化），这部分包含在热口径的 443ms 里，本项不动它。

### 预置目录里有什么

`migrate` 只写 schema 与 `schema_migrations` 记账行，不写任何用户数据（用户、工作区等种子数据由 hub/local 在 DB 打开之后的代码创建，不在迁移内）。因此一份「用发布版代码对空目录跑完 `createLocalDb` 并干净关闭」的数据库目录就是纯 schema 的首次运行种子，不含任何人的数据。PGlite 集群目录在干净关闭后是自洽的文件集，可整体搬移。

## 设计

### 种子规则（唯一的使用点）

本地运行时在调 `createLocalDb(paths.db)` 之前检查 `<home>/db` 是否存在：

- **不存在**（首次运行，或用户自行删库后的等价情形）：先把随包的预置种子落到 `<home>/db`，再照常 `createLocalDb`——`migrate` 发现全部迁移已应用，零个待执行，直接打开。
- **已存在**：与今天完全一致，预置不参与。既有安装升级到带预置的版本时不受影响；新版本新增的迁移照常在既有库上执行。

不做任何合并、覆盖或版本间复用：每个发布包只带自己这一版的种子，只用于该版本进程的首次运行。

### 种子的生成

在桌面打包流水线内、按 target 在其原生 runner 上生成：用该 target 发布代码对临时目录执行一次 `createLocalDb` 并 `close()`，得到已应用全部迁移的集群目录，再按 D-2 的形态打包进该 target 的载荷。构建断言：种子内 `schema_migrations` 的集合与随包的迁移文件集合**恰好相等**，不等则构建失败——种子与代码漂移在发布前就被拦住，而不是到用户机器上才发现。

按 target 在原生 runner 生成，也绕开了「一份集群目录能否跨平台/跨架构搬移」的问题：win32-x64 的种子在 Windows runner 上生成，darwin-arm64 的在 macOS runner 上生成，各自只被同 target 的包使用。

### 打包形态

两个候选，D-2 定案：

- **A：单个归档文件**。种子以一个归档（如 tar/zip）随包，首次运行时解开到 `<home>/db`。载荷里是一个大文件，解压是顺序 I/O。
- **B：松散目录**。种子以原始目录树随包，首次运行时整树拷贝。文件数以百计的小文件拷贝恰好是 Windows 上最慢的 I/O 模式之一，与本项要绕开的成本同源。

本文推荐 A，但要求实施的第一步在 windows-latest 上实测两种形态的「落到 `<home>/db` 就绪」耗时（同一份种子内容），把数字记进实施记录；若 B 反而显著更快且实现更简单，可按实测改选 B 并在计划里注明理由。

### 失败回退

种子落地失败（归档损坏、磁盘满、权限错误、标记不符）时：删掉未落完的半成品目录，回退到今天的行为——对空目录 `createLocalDb` 全量初始化。回退只写一条诊断记录（启动日志/`startup-phase` 的既有通道），**不阻塞启动、不弹窗**。种子是优化，不是新的失败模式。

### 载荷记账

种子会给安装包增加字节。v0.3.1 的载荷口径是 win32-x64 75.1 MiB / darwin-arm64 72.9 MiB（上限 80 MiB）。本项要求：种子归档的实测大小按 target 记进桌面发布的 payload 报告（单列一行 `preset-db`），并受 D-6 的上限约束；超限则回到 D-2/D-6 重新定案，不静默放行。

## 安全不变量

- 种子只含 schema，不含任何用户数据、凭证或示例内容；生成过程在 CI 内用发布代码完成，种子不从任何外部来源下载。
- 种子落在 `<home>/db`，而 home 目录本身在运行时创建时已按既有机制收紧权限（`resolveHome` 的 `protectPrivatePath`，0700）；种子落地发生在同一 home 内，不新增暴露面，也不改变任何 ACL 检查的次数与时机（2026-11-10 设计的「每次检查仍执行」继续有效）。
- 种子完整性由构建断言（迁移集合相等）与发布流水线本身保证；运行时不信任任何标记文件来跳过 `migrate`——`createLocalDb` 仍照常跑 `migrate`，种子只是让它无事可做。即使种子被篡改成旧 schema，`migrate` 也会把缺的迁移补上；被篡改成坏集群时 PGlite 打开失败，按当时的既有失败路径呈现，不静默吞掉。

## 验收口径

沿用 #186 W2 的口径，不发明新数字：

- **功能**：自动化测试覆盖种子规则两条分支（db 不存在 → 落种子后打开、迁移零待执行；db 已存在 → 不触碰）、回退分支（种子损坏 → 全量初始化成功且有诊断记录）、构建断言（迁移集合不等 → 构建失败）。
- **数字**：CI `startup-sample` 增加一个「预置首次」口径（全新 home + 落种子 + `createLocalDb`），与既有冷/热同跑；验收看 windows-latest 最近 5 次运行的中位，对照 D-6 的门槛。macOS 同口径记录，只作参考不设门槛（其冷中位未触发）。
- **口径区分**：以上是 CI runner 数字与自动化测试，不是真实用户硬件验收；按 2026-11-16 测试政策，桌面实机不主动测。
