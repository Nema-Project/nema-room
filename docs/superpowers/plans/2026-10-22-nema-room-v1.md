# Nema Room v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 本地运行的 Nema Room 第一版。用户在某个 workspace 的聊天里随手扔文本，本机 `nema` daemon 用用户自己的 Codex 订阅，在隔离环境中运行 Agent。Agent 只通过 Room MCP 把内容整理成 git 版本化的项目知识，并在聊天里回报改动、一次追问一个问题。界面为 Slack 式三栏、瑞士风格，支持日英中三语。

**Architecture:** 三个进程全部跑在用户笔记本上：
- `hub`：Hono HTTP 服务，提供 UI REST + SSE、daemon WebSocket、Room API；PostgreSQL 存聊天、任务和设置，每个 workspace 一个 git 仓库存知识。
- `web`：Next.js UI，直接调用 hub。
- `nema` CLI：`nema daemon` 领取任务、为 workspace 准备隔离的 `CODEX_HOME`、启动 `codex exec`；`nema mcp` 是被 Codex 拉起的 stdio Room MCP，转发到 hub 的 Room API。

服务端不调用任何模型。

**Tech Stack:** TypeScript（Node ≥ 22，npm workspaces）、Hono + `@hono/node-server` + `ws`、PostgreSQL 17（开发用 Docker；测试用 `@electric-sql/pglite`）、`zod`、`@modelcontextprotocol/sdk`、`commander`、`smol-toml`、`gray-matter`、Next.js（App Router）+ React、`react-markdown` + `remark-gfm`、`diff`、Vitest + Testing Library、系统 `git` CLI、Codex CLI（本机已装 0.148.0）。

**Spec:** `docs/superpowers/specs/2026-10-21-nema-room-design.md`（含 2026-10-22 补充的 4.6 界面设计）；草图：`docs/design/ui-main-room.html`、`docs/design/ui-entry-detail.html`。

**Supersedes:** `docs/superpowers/plans/2026-10-21-nema-room-v1.md`（已删除；按更新后的 spec 重写）。

## Global Constraints

- 服务端只监听 `127.0.0.1`（spec 6.5）。端口：hub `4400`，web `3000`，Postgres `5433`。
- 服务端不调用模型，不持有任何模型 API key（spec 6.2）。
- 新建 workspace 默认 `confidential = true`、`knowledgeLanguage = "follow"`（spec 5.2、4.6）。第一版没有任何跨 workspace 功能（spec 5.3）。
- Room MCP 是 Agent 读写知识的唯一入口；每次知识修改 = 该 workspace 仓库里的一次 git commit，commit 带来源消息 id 与理由（spec 4.4、6.2、6.3）。
- 知识仓库目录固定为 `requirements/`、`decisions/`、`tradeoffs/`、`questions/`、`sources/`，每条一个 `<id>.md`（spec 4.1、6.3）。
- 团队可见数据（知识条目 + 外部来源）与仅本人可见数据（聊天消息）分开存放：知识仓库里只存消息 id，不存原始聊天文本（spec 3）。
- 第一版只接 Codex；daemon 通过 `AgentAdapter` 接口调用，Claude Code / Cursor 以后各加一个适配器（spec 6.2）。
- 同一 workspace 的任务串行；所有 Codex 运行全局串行（spec 4.5、6.6）。
- 每次 Agent 运行都是无状态的：上下文由 hub 每次重新组装（spec 4.5）。
- 聊天里一次只追问一个问题：由 hub 在任务结束时**确定性地**挑出优先级最高的 open question 展示，Agent 的回复正文不写问题（spec 4.3、4.5）。
- spec 6.6 的 8 条隔离措施全部落地：
  1. 每个 workspace 独立的 0700 配置目录，配置从零生成；
  2. `auth.json` 只软链接、不复制；
  3. 凭证存在钥匙串里时拒绝启动；
  4. 只注入 Room MCP；
  5. 关闭记忆、历史、会话落盘、网页搜索、遥测、更新检查；
  6. 每次运行用全新的临时工作目录，且不在任何 git 仓库内；
  7. 环境变量白名单；
  8. 运行前自检。
- UI（spec 4.6）：
  - 界面语言：日 / 英 / 中三语，首次跟随浏览器语言，缺失的文案回退英文。
  - 颜色：只用黑、白、灰；红色 `#e3241b` 只用于"需要你处理"的内容。
  - 侧栏用纸白 `#f3f2ee`。
  - 字体：Inter + PingFang SC / Hiragino Sans + JetBrains Mono。
  - Enter 换行，Shift+Enter 发送；消息支持 Markdown。
  - Agent 显示名「Nema」。
  - 只做桌面布局。

## Review Focus

1. **daemon 在运行中断开或崩溃**：任务不能永远停在"运行中"（Multica #5701 就是这个问题）。期望：daemon 断开时，它手上 running 的任务回到 queued，重连后重新派发。→ Task 5、Task 8 加测试。
2. **用 A workspace 的 run token 访问 B workspace，或任务结束后还在用旧 token**：期望返回 401/404，绝不返回数据。→ Task 6 加测试。
3. **用日文 / 中文输入法输入时按 Enter 或 Shift+Enter 确认候选词**：期望输入法组字期间的按键只交给输入法处理，不发送、不插入多余换行。→ Task 12 加测试。
4. **随手记录或 Agent 输出里含有 HTML / `<script>` / `javascript:` 链接**：期望按纯文本显示，不执行；链接只允许 http/https/mailto。→ Task 12 加测试。
5. **Codex 未安装、未登录、凭证在钥匙串里、非零退出，或调用了 Room 以外的 MCP server**：期望任务以清楚的中文错误失败、错误贴进聊天，该 workspace 的下一条任务继续处理。→ Task 9、Task 10 加测试。

### Task 1: Monorepo 骨架与共享类型

**Files:**

**Interfaces:**
- Produces（`@nema/shared`）:
  - `type EntryKind = "requirement" | "decision" | "tradeoff" | "question" | "source"`
  - `KIND_DIR` = `{requirement:"requirements", decision:"decisions", tradeoff:"tradeoffs", question:"questions", source:"sources"}`；`KIND_PREFIX` = `{requirement:"R", decision:"D", tradeoff:"T", question:"Q", source:"S"}`
  - `kindFromId(id: string): EntryKind | null`（`/^(R|D|T|Q|S)-[1-9]\d*$/`）；`idNumber(id: string): number`
  - `EntryFrontmatter` zod：
    - `id`、`kind`、`title`（1..200）、`status`、`businessDate`（`"YYYY-MM-DD" | null`）、`related: string[]`、`sourceMessages: string[]`
    - `url?`：仅 source，必填，必须是 http/https
    - `priority?: 1|2|3`：仅 question，必填
  - status 取值：requirement `active|superseded|dropped`；decision `active|superseded`；tradeoff `active`；question `open|resolved`；source `active`。`INACTIVE_STATUSES = ["superseded","dropped","resolved"]`
  - `type Entry = EntryFrontmatter & { body: string }`；`type EntrySummary = Pick<Entry,"id"|"kind"|"title"|"status"|"businessDate"|"priority"|"url"|"related">`
  - `UpsertEntryInput` zod：
    - 字段：`id?`、`kind`、`title`、`body`、`status?`、`businessDate?`、`related?`、`sourceMessages`、`url?`、`priority?`、`reason`（1..500）
    - `sourceMessages: string[]` 默认 `[]`。"至少一条"由 Room API 强制，见 Task 6
  - `workspace.ts`：
    - `type KnowledgeLanguage = "ja" | "en" | "zh" | "follow"`；`KNOWLEDGE_LANGUAGES`
    - `AgentMessageMeta` zod = `{ changes: {entryId: string; kind: EntryKind; title: string; op: "add"|"update"}[]; askedQuestion: {id: string; title: string; body: string} | null }`
  - `protocol.ts`：
    - `DaemonToHub` = `hello{token, version, adapters: string[]}` | `task.event{taskId, event:{type:"progress"|"agent_message"|"tool_call", text}}` | `task.finished{taskId, ok:true, reply} | {taskId, ok:false, error}`
    - `HubToDaemon` = `welcome{}` | `task.assign{taskId, workspaceId, adapter:"codex", prompt, runToken, hubUrl}` | `error{message}`
    - 导出 `parseDaemonToHub(raw)` / `parseHubToDaemon(raw)`（失败时抛 `ZodError`）
    - 导出 `type TaskAssign = Extract<HubToDaemon,{type:"task.assign"}>`、`type TaskEvent = Extract<DaemonToHub,{type:"task.event"}>["event"]`
  - `roomApi.ts`：`ListEntriesResponse = {entries: EntrySummary[]}`、`GetEntryResponse = {entry: Entry}`、`UpsertEntryResponse = {entry: Entry, commit: string}`

### Task 3: 知识历史：带版本号的 history、版本内容、段落级"为什么"

**Files:**
- Create: `packages/knowledge/src/history.ts`
- Modify: `packages/knowledge/src/index.ts`
- Test: `packages/knowledge/test/history.test.ts`

**Interfaces:**
- Consumes: Task 2 的 `git`, `parseCommitMessage`, `KnowledgeStore`
- Produces:
  - `type HistoryItem = { version: number /* 最早一版 = 1 */; commit: string; committedAt: string /* ISO */; op: "add"|"update"; reason: string; sourceMessages: string[]; author: "agent"|"user"; taskId?: string }`
  - `history(repoDir: string, id: string): Promise<HistoryItem[]>`：按新到旧排列
  - `versionAt(repoDir: string, id: string, commit: string): Promise<Entry>`
  - `type ParagraphBlame = { text: string; version: number; commit: string; reason: string; author: "agent"|"user" }`
  - `blameParagraphs(repoDir: string, id: string): Promise<ParagraphBlame[]>`：只处理 body，不含 frontmatter

段落划分规则：按空行把 body 切成块；标题行（`#` 开头）与紧跟其后的块合并成一段。某一段的版本，取这段里所有行中最新的那次 commit（spec 4.6 "按段落标注"）。

- [ ] **Step 1: 写失败测试**：
  - 建 R-1，body 为 `"## 背景\n客户嫌慢\n\n## 验收标准\n待确认"`；然后只改验收标准，reason 为 `"Q-4 的回答"`；再改状态。
  - 断言 `history`：长度为 3，版本号依次 `[3,2,1]`，`[2].op === "add"`。
  - 断言 `versionAt(v1 的 commit).body` 含 `"待确认"`。
  - 断言 `blameParagraphs`：结果有 2 段；第 1 段 `version 1`；第 2 段 `version 2`，`reason "Q-4 的回答"`。
  - 不存在的 id：`history` 返回 `[]`，`versionAt` 抛错。
- [ ] **Step 2: 运行**，应 FAIL。
- [ ] **Step 3: 实现**：
  - history 用 `git log --format=%H%x00%cI%x00%B%x1e -- <path>`；
  - versionAt 用 `git show <commit>:<path>`；
  - blameParagraphs 先用 `git blame --porcelain <path>`，跳过 frontmatter 行，再按上面的规则聚合；commit → reason/version 的映射由同一次调用的 `history` 结果提供。
- [ ] **Step 4: 运行**，应 PASS。

4. 进程结束后：
   - 退出码 0：reply 取 `last.txt` 的内容；为空则取最后一条 agent_message；仍为空则返回 `"Agent 没有返回回复"`。
