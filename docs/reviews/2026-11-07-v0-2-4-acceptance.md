### 仍要在真机上做的

不要把下面任何一项交给这台 Linux 机器或一个 mock 窗口。也不要为了这项验收去连维护者自己的日常机器；用一次性的 Windows x64 和 macOS arm64 环境，数据目录用临时位置或一套专门用来升级的旧安装。

1. 在对应平台上，从准备发布的那个提交打安装包（Windows：`npm run desktop:make -- --platform win32 --arch x64`；macOS arm64：该平台的 DMG）。记下安装包 SHA256，以及包内 `resources/payload/runtime-manifest.json`（macOS 是 `Contents/Resources/payload`）的 `commit`。
2. 冷启动和热启动：在同一提交的检出里执行 `npm run desktop:bench -- --app <可执行文件> --runs 3`。脚本自己把 `HOME`、`NEMA_DESKTOP_TEST_HOME`、`NEMA_DESKTOP_TEST_USER_DATA` 指到临时目录，并设置 `NEMA_DESKTOP_BENCH=1`，跑完删除。保存 stdout 的 JSON。Windows 报告里要有 PowerShell ACL 的次数和总时间；macOS 没有这一项。这只是打包进程的冷、热启动，不是覆盖安装。
3. 普通启动（不带 bench）时，进程起来后 1 秒内要有窗口，背景跟主题一致，中间不闪白屏。把一份拷贝的 payload 弄坏后再启动，错误要留在这个窗口里，而不是只弹出模态框；测完恢复拷贝。
4. 覆盖升级和旧数据：先安装已发布的 v0.2.3，做出一个工作区、一条聊天、一个 thread、一条知识，退出。再用候选安装包覆盖安装到同一用户位置，重新打开。这四样还在，并且如果上次停在那个房间，启动会进那个房间。`upgradeRecovery.test.ts` 不能代替这一步。

未做、也不在 PR #213 里的：冷启动 PGlite 迁移改造，以及把多次文件 ACL 合成一次 PowerShell。

## 2. 多账户 S5.2（[issue #131](https://github.com/Nema-Project/nema-room/issues/131)）

S5.1 已随 PR #202 合入。`docs/guide.zh.md` 仍写明：真实账户上的切换还没有验收记录，现有证据是假提供商上的自动化测试。这次没有两个明确交给 Nema 验收的真实账户，也没有可以安全、可控地产生限流的账户。没有发真实请求，所以没有额度消耗。

因此下面全部标为未测，假 provider 的通过也不能改这个结论：

- 手动模式选账户 A 跑一条任务，回复下方是 A；再选 B 跑一条，回复下方是 B。
- 自动模式遇到真实 429 或额度用尽时是否换账户，`attempts` 里有什么，回复下方的句子是什么。
- 一个没有声明图片能力的账户：自动模式拒绝带图片的任务并且不发出请求；手动模式仍会发出。后一项会打到真实提供商，可能计费，做之前要先确认费用。

不要为了逼出 429 去打满额度或堆大量请求。只有在已经处在限流、或有一个不会产生不确定费用的可控 429 时才补这一项。

假 provider 的自动化标准在 `apps/cli/test/routing/acceptance-auto.test.ts`（默认关、429 换到第二个账户、401 不换、开始输出后不换、新账户的第一次请求没有 `encrypted_content`、能力都不满足时零请求）。那是自动化证据，不是 S5.2。
