## 1. 附件（图片 / PDF / 文本；投递上限 8 个或 32 MiB）

### 1.1 Nema 现在的做法

- **上限与预算**在 [packages/shared/src/attachments.ts](../../packages/shared/src/attachments.ts) 第 9–18 行：图片 10 MiB、PDF 20 MiB、文本 512 KiB；一次任务最多 8 个、合计 32 MiB；未发出的上传 24 小时后清理（`stagedTtlMs`）；所有附件合计默认 2 GiB（`defaultGlobalBytes`）；数据盘剩余低于 1 GiB 时拒收（`minFreeBytes`）。
- **类型判定只看字节。** 第 70–94 行的 `sniffAttachment` 先用魔数判 PNG/JPEG/GIF/WebP/PDF，扩展名必须与字节一致（第 75–78 行）；文本要求严格 UTF-8、不含 NUL（第 85–93 行）；SVG 无论叫什么名字都拒收（第 92 行，注释写明它是 active content）。
- **落盘与配额。** [apps/hub/src/attachments.ts](../../apps/hub/src/attachments.ts) 第 288 行起是 `AttachmentStore.upload`；第 273–286 行的 `reserve` 在进程内原子预留字节，超全局配额或不足 1 GiB 余量返回 507；第 295 行对超过任何类型上限的文件先返回 413；第 343–352 行写到 `.staging` 临时文件、fsync、改名，路径只用服务端 id；第 387–426 行在写入过程中按魔数决定类型上限并二次校验；第 210–216 行的 `privateDir` 建 `0700` 目录，第 388–390、467 行把文件设成 `0600`。
- **过期与墓碑。** 第 552–577 行的 `sweep` 把过期的 `staged` 标成 `expired` 并删文件；删除只标墓碑，文件删不掉就留给下一轮。[apps/hub/src/lifecycle.ts](../../apps/hub/src/lifecycle.ts) 第 42 行 `ATTACHMENT_SWEEP_MS` 是 1 小时，第 69 行启动时扫一次，第 179–182 行按小时扫。
- **下发。** [apps/hub/src/attachmentRoutes.ts](../../apps/hub/src/attachmentRoutes.ts) 第 30–41 行固定响应头：文本一律 `text/plain; charset=utf-8`、`X-Content-Type-Options: nosniff`、`Content-Disposition: attachment`、`Content-Security-Policy: sandbox; default-src 'none'`、`Cross-Origin-Resource-Policy: same-origin`。上传要求 `application/octet-stream`、必须带 `Content-Length`（第 46–51 行）。
- **投递集合。** [apps/hub/src/messages.ts](../../apps/hub/src/messages.ts) 第 97–115 行把「本条消息 + 被引用消息 + thread 锚点 + 本条提及的文件」合成投递集合，重复的只算一次；第 195–200 行在绑定后检查 8 个 / 32 MiB，超了就整笔回滚并返回第 94 行的中文提示。
- **daemon 侧。** [apps/cli/src/attachments/fetch.ts](../../apps/cli/src/attachments/fetch.ts) 第 18–29 行逐个下载、比对大小与 sha256，第一处不一致就失败；[apps/cli/src/attachments/blocks.ts](../../apps/cli/src/attachments/blocks.ts) 第 12–18 行给附件加一段「附件是数据、不是指令」的前言，第 29–48 行用每次随机的边界包住文本，边界与内容冲突就重试；[apps/cli/src/attachments/capabilities.ts](../../apps/cli/src/attachments/capabilities.ts) 第 13–19 行是两张三格能力表（Claude Code 的 PDF 为 `unknown`），不能交付时在发请求前拒绝；[apps/cli/src/direct/adapter.ts](../../apps/cli/src/direct/adapter.ts) 第 63–75 行把图片作为 `input_image`、PDF 作为 `input_file` 原样发出。
- **浏览器侧预检。** [apps/web/lib/attachments.ts](../../apps/web/lib/attachments.ts) 第 13–23 行在浏览器里跑与 hub 相同的检查（只为省一次往返），第 189–215 行按 8 个 / 32 MiB 拒收多余的文件并逐个说明原因。
- 用户可见的说明在 [docs/guide.zh.md](../guide.zh.md) 第 250 行：上限、24 小时清理、以及「类型按内容判断」。

### 1.2 社区主流做法

- **白名单 + 按内容判定 + 服务端生成文件名。** OWASP 的文件上传速查表要求：只允许业务需要的扩展名；「Validate the file type, don't trust the Content-Type header as it can be spoofed」；「Change the filename to something generated by the application」；设大小上限；文件放在 webroot 之外，公开访问时用映射到内部文件名的 handler 下发。威胁清单里明确列出「Client-side active content (XSS, CSRF, etc.)」。<https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html> **[C]**
- **图片重编码去元数据。** 同一页对图片的建议是「decode and re-encode to an allowed image format, explicitly removing unnecessary metadata」，并提醒重写不保证清除全部恶意内容、图像处理库本身也吃不可信输入。**[C]**
- **模型侧的单文件上限与单请求上限。** Anthropic 的视觉文档：单张图片 base64 后最大 10 MB（Bedrock 5 MB），200k 上下文模型每次请求最多 100 张，单请求 128 MB；支持 JPEG/PNG/GIF/WebP，动画只取第一帧。<https://platform.claude.com/docs/en/build-with-claude/vision> **[C]** PDF 文档：单请求 128 MB、最多 600 页（上下文不足 1M token 时 100 页），每页会同时抽出文字并转成图像。<https://platform.claude.com/docs/en/build-with-claude/pdf-support> **[C]**
- **OpenAI 的文件输入。** 每个文件必须小于 50 MB，一次请求里所有文件合计 50 MB；PDF 抽文字加页图，非 PDF 只抽文字。<https://platform.openai.com/docs/guides/pdf-files> **[C]**
- **聊天产品的附件与墓碑。** Slack 上传文件后「Slack will scan the file for malware before making it available」，上传分三步（取 URL、传字节、`files.completeUploadExternal` 把多个文件挂到一条消息），移除一个远端文件后原位置显示「This file was deleted.」<https://docs.slack.dev/messaging/working-with-files/> **[C]** Discord 发消息时「The maximum request size when sending a message is 25 MiB」，附件对象带 id、filename、description 与大小。<https://docs.discord.com/developers/resources/message> **[C]**
- **SDK 对坏图片块的降级方式。** Claude Code 的流式输入文档写：图片块 `source` 缺失或不是对象时 SDK 不报错，「sends Claude a text note in place of the image, such as `[Image could not be processed: ...]`, and the session continues」。<https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode> **[C]**

### 1.3 差距与原因

- **上限比社区低，是有意的。** 单类 10 / 20 / 0.5 MiB 与每次 8 个 / 32 MiB，都远低于 Anthropic 与 OpenAI 的单请求容量，也低于 Discord 单条消息 25 MiB 的量级。Nema 的一次任务等于一条讨论消息，附件是「这次讨论的输入」而不是文件传输，所以预算按上下文成本定，不由接口能力定。**[I]** 这是刻意偏离。
- **类型白名单与「按内容判定」与 OWASP 一致。** 拒绝 SVG 的理由对应 OWASP 列出的「客户端主动内容」威胁；文件名不参与路径、下发带 `nosniff` 与 sandbox CSP，对应 OWASP 的 handler 模式。**[I]** 一致，不需改。
- **不重编码图片、不剥元数据——遗漏。** OWASP 明确建议对图片解码再编码并去掉不必要的元数据；Nema 是把原字节原样发给提供商（[apps/cli/src/direct/adapter.ts](../../apps/cli/src/direct/adapter.ts) 第 75 行），EXIF 里的位置、设备信息随之发出，用户在界面上看不到这件事。指南第 250 行只写了类型与上限，没有写「原样转发、元数据保留」。
- **不做恶意文件扫描——刻意，但理由没写下来。** Slack 在文件可用前扫恶意内容；Nema 没有这一步。单用户本地部署、附件不渲染、文本强制成 `text/plain` 都能降低风险，但这些理由在 spec 或指南里都没有成文记录。**[I]**
- **配额粒度是全局而不是按 workspace——刻意。** 设计文档 [2026-10-30-chat-attachments-design.md](../superpowers/specs/2026-10-30-chat-attachments-design.md) 的 D-1 一节写明这只是「防止把 hub 所在的磁盘写满，不是按 workspace 的配额」。**[C]**
- **拒绝而不是降级——刻意。** Claude Code SDK 遇到坏图片会插一段文字继续；Nema 的选择是让任务失败并附提供商原文（能力表与 CHANGELOG 都写了「不重试、不降级、不把 PDF 转成文字」）。理由是 #45 的「agent 看到的东西必须和用户以为它看到的一致」：静默替换会让用户以为模型看过原件。**[I]** 这一处与社区最常见的 SDK 行为不同，但理由成立。

### 1.4 建议

**值得现在做**

1. 在指南的附件一节补两句事实说明：图片与 PDF 以原字节转发，文件自带的元数据（例如图片的 EXIF，可能含拍摄地点）会一并发给模型提供商；拒绝的类型（SVG、Office、压缩包、音视频）各自为什么拒绝。纯文档改动，不改行为。
2. 在 `SECURITY.md` 或技术参考里记下「不扫恶意文件」这一已知边界与它的缓解措施（不渲染、文本强制 `text/plain`、nosniff + sandbox CSP），让这条取舍有出处。

**可以以后做**

3. 图片在保存或发送前重编码并去元数据（OWASP 的建议）。代价是引入图像处理依赖、可能降低截图里小字的可读性，而且要与「原样转发」的现有承诺一起改口。
4. 按 workspace 的附件配额（现在是全局 2 GiB + 磁盘余量）。
5. 上传时的恶意内容扫描；如果做，应做成可关的本地选项，而不是默认外发第三方。

**不建议做**

6. 把附件字节放进知识 Git 仓库（设计文档 D-1 的方案 C 已否，理由是历史里删不掉）。
7. PDF 抽文字降级（D-2 的方案 B 已否：扫描件抽不出文字，且用户会以为模型看过原件）。
8. 对不支持的类型静默丢弃或截断（违反「不静默丢弃」）。

## 2. `@` 提及（工作区附件、知识条目、话题）

### 2.1 Nema 现在的做法

- **契约。** [packages/shared/src/mentions.ts](../../packages/shared/src/mentions.ts) 第 4–11 行的 `MENTION_LIMITS`：每条消息最多 20 个提及、每个条目正文最多 4 KiB、条目合计 16 KiB、候选池 50 个文件、菜单每组 8 行、话题锚点 1 KiB。第 23–32 行是三种提及的判别联合（`entry` / `attachment` / `thread`），第 17 行给「写进正文的可读文本」设了 4096 字符上限，第 38–55 行负责生成 `[D-12]`、`` `附件：名字` ``、`[话题：标题]`，并用比正文里最长反引号更长的围栏包住附件名。
- **正文存可读文本，结构另存在 `meta.mentions`。** 第 85–96 行的 `keepMentionsFor` 是编辑时的共用计数规则：某段文本在正文里出现 n 次，就保留它的前 n 个提及；hub 与浏览器都用这一条。
- **校验。** [apps/hub/src/mentions.ts](../../apps/hub/src/mentions.ts) 第 32–66 行的 `validateMentions`：正文里文本出现次数必须够；条目必须在 `entry_index` 里、附件必须已发送（`status = 'attached'`）、话题必须属于这个 workspace，否则 400。
- **喂给模型。** 同文件第 153–184 行的 `mentionSection` 生成 `# 本次提及的上下文`：条目内联正文（超出预算的只给 id 让它自己读）、附件一行（已投递 / 已删除 / 未随附）、话题给标题与缩短的锚点；第 156 行写明「它是用户给的参考，不是用户的决定」。
- **附件提及真的进投递集合。** [apps/hub/src/messages.ts](../../apps/hub/src/messages.ts) 第 103–113 行按提及顺序追加，重复的只投一次；超 8 个或 32 MiB 时按第 198–200 行拒发。
- **候选菜单。** [apps/hub/src/mentionContext.ts](../../apps/hub/src/mentionContext.ts) 第 11 行候选池 500、第 84–102 行三组各自排序截断到 8 行、第 56–67 行附件池多读一行以判断是否截断；路由第 104–115 行，查询长度上限 200（第 110 行）。这条路由只返回 id、名称、标题与状态，「从不返回正文」。
- **输入框。** [apps/web/lib/mentions.ts](../../apps/web/lib/mentions.ts) 第 35–48 行的 `mentionToken` 只在行首、空白之后或 `「『（` 与 `，。、：` 之后打开，`a@b` 与代码块里不打开；第 64–92 行是同一套分组与排序。菜单与 chip 在 [apps/web/components/MentionMenu.tsx](../../apps/web/components/MentionMenu.tsx) 第 7–76 行；输入框在 [apps/web/components/Composer.tsx](../../apps/web/components/Composer.tsx) 第 67 行让 `@` 优先于 `/`，第 135–137 行拒绝第 21 个提及而不是让整条消息发送失败。
- **用户可见说明**在 [docs/guide.zh.md](../guide.zh.md) 第 258 行（一组菜单、可读写法、chip、`a@b` 与代码块不打开、20 个上限、提及不改变条目状态）。
- **为什么没有 tag 与成员：** 设计文档 [2026-10-31-mentions-design.md](../superpowers/specs/2026-10-31-mentions-design.md) 第 43–56 行的「社区做法对照」与「偏离主流的地方和理由」（第 43–50 行是对照，第 52–56 行是偏离）已经写了取舍；tag 提及与成员提及分别推到了 #162、#163，原因是知识条目没有 `tag` 字段、也没有 `users`/`members` 表与消息作者。

### 2.2 社区主流做法

- **结构化 id 写在正文里，显示靠客户端渲染。** Slack 要求用用户 id：`Hey <@U012AB3CD>, thanks for submitting your report.`，并说明「the ID will be automatically converted to show the display name of the user」；群组是 `<!subteam^ID>`；还明确建议关掉自动解析以避免用户输入里的 `@everyone` 被误当成提及。<https://docs.slack.dev/messaging/formatting-message-text> **[C]**
- **允许提及的白名单。** Discord 的 `allowed_mentions` 字段控制哪类提及会被解析，「This field is always validated against your permissions and the presence of said mentions in the message, to avoid "phantom" pings」；消息体里没有的提及不会被通知。<https://docs.discord.com/developers/resources/message> **[C]**
- **一个 `@` 菜单、分种类、可精确引用。** Linear 编辑器文档：「Write `@text` to mention a user, issue, project, date, document, or pull request」；`@ENG-123` 直接引用 issue，被引用的 issue 会自动加为 related。<https://linear.app/docs/editor> **[C]**
- **编辑器里的上下文提及。** Cursor 文档：`@` 可附文件/文件夹、终端输出、历史聊天、git diff 与内建浏览器；并建议「Use @ mentions when you know which files are relevant. If you're not sure which files matter, skip it」。<https://cursor.com/docs/context/mentions> **[C]**
- **结构化提及 + 可读文本并存。** GitHub 的 Markdown 支持 `@user` 与 `@org/team` 触发通知，并说明「A person will only be notified about a mention if the person has read access to the repository」。<https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax> **[C]**

### 2.3 差距与原因

- **正文存可读文本而不是 id——刻意，且与 Slack/Discord 相反。** 主流做法在正文里存 `<@U…>` 这类不透明 id，渲染时换成名字。Nema 反过来：正文是真文字（`[D-12]`、`` `附件：名字` ``），id 存在 `meta.mentions` 里。原因是 Nema 的正文会被写进知识条目引文（`quotes` 要求逐字复制用户原话），可读文本让引文在脱离渲染器时仍然成立；代价是名字改了就断链，这一点靠「编辑时按文本出现次数裁剪提及」与「提及只作参考」来兜底。**[I]** 设计文档第 49 行的「结构化存储」一条记了这条偏离。
- **没有通知语义——有意。** Slack/Discord/GitHub 的提及本质是「通知某个人」；Nema 的提及是「把某个对象交给这一次任务」，工作区只有一个人，所以不存在通知对象。成员提及要等身份模型（#163）。**[I]**
- **不做自动解析、不做隐式提及——与 Slack 的建议一致。** Slack 明确推荐手动写法、关掉自动解析；Nema 根本没有「文本里出现 `@名字` 就自动当成提及」这条路，提及只能来自菜单或精确 id，服务端再校验文本出现次数。**[I]** 一致。
- **候选池是固定上限而不是搜索。** 500 条候选 + 8 行分组 + 200 字符查询，意味着工作区很大时菜单只能看到「最近更新的」一批。主流产品一般直接做服务端搜索（Linear 的 issue 搜索、Cursor 的文件索引）。这是刻意的规模取舍（避免每次按键扫全库），但一旦单 workspace 条目数上千，用户会感知到「想提的东西不在列表里」。**[I]**
- **编辑时静默丢提及——刻意，但用户看不到提示。** `keepMentionsFor` 的规则是「文本删了就丢提及」，指南第 258 行写了这条规则，但界面上不会在保存后告诉用户「有 2 个提及因为文本被删而失效」。**[I]**

### 2.4 建议

**值得现在做**

1. 提及因编辑失效时给一次非阻塞提示（例如编辑保存后的一行「已移除 2 个失效的提及」）。后端已经有 `keepMentionsFor` 的结果，前端只差一处对比与一句文案。

**可以以后做**

2. 候选池换成服务端分页/搜索，或把 `MENTION_POOL` 与 `menuPerGroup` 做成可配置，让条目多的 workspace 仍能找到目标。
3. 给 `[话题：标题]` 与 `` `附件：名字` `` 也提供「按 id 精确提及」（现在只有条目能 `@D-12`）；附件名重名时目前只能靠菜单里的先后顺序区分。
4. 若以后做多用户（#163），再引入 Slack/Discord 那种「结构化 id + 渲染时取名」的存储，而不是现在改。

**不建议做**

5. 自动把正文里出现的 `@xxx` 解析成提及。Slack 明确说这会误触发；Nema 的 `a@b` 例外规则也是为了同一目的。

### 3.2 社区主流做法

- **三级渐进披露。** Agent Skills 规范把加载分成：元数据（约 100 token，启动时全部加载）、`SKILL.md` 正文（激活时加载，建议 < 5000 token）、资源文件（按需）；并建议「Keep your main `SKILL.md` under 500 lines」，引用「one level deep」。<https://agentskills.io/specification> **[C]** Anthropic 的最佳实践页给出同一口径：正文控制在 500 行以内、拆到单独文件、引用只保留一层（「Keep references one level deep from `SKILL.md`」）。<https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices> **[C]**
- **Anthropic 的同一套分层。** 官方文档把这三层写成 Level 1 元数据（约每个 Skill 100 token）、Level 2 指令（激活时读 `SKILL.md`）、Level 3+ 资源与代码（脚本运行而不进上下文）。<https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview> **[C]**

- **Claude Code 的 `/skill-name` 与命名规则。** Claude Code 文档：技能即 `/skill-name`；命令名来自目录名或 frontmatter 的 `name`；插件技能带命名空间 `/plugin:skill`；`disable-model-invocation` 与 `user-invocable` 双向控制谁能调用；`allowed-tools` 只在调用那一轮授权、下一条消息即失效。<https://code.claude.com/docs/en/skills> **[C]**

### 3.3 差距与原因

- **没有 `scripts/` 执行能力——刻意，且是本产品最根本的一条边界。** 规范与三个实现都把「脚本由 agent 用 bash 运行」当成正常能力；Nema 的 daemon 只给 Agent Room 工具，不开放 shell 与文件系统。因此 `read_skill` 只读正文与 Skill 目录内的文件（[apps/cli/src/skills/safeRead.ts](../../apps/cli/src/skills/safeRead.ts) 拒绝越界与链接），缺口在 `gaps.ts` 里如实列出。**[I]** 这条偏离与 #45、「不把 Nema Room 变成通用 agent 运行时」一致。
- **`allowed-tools`、`paths`、`hooks`、`context: fork` 只解析不生效。** `frontmatter.ts` 读这些字段，但 `gaps.ts` 第 27–30 行把它们标成缺口。主流实现里 `allowed-tools` 是有实际授权效果的（Claude Code 文档写明「The grant clears when you send your next message」），Nema 若照做会等于自己发明一套工具授权模型。**[I]** 刻意。
- **`name` 与目录不一致只记诊断、不拒载——偏离规范。** 规范要求「Must match the parent directory name」，Claude Code 也按目录名决定命令名。Nema 的 `parseSkillFile`（第 155 行）只把不一致写进诊断，Skill 仍然加载并在菜单里按 id 出现，用户可能看到「目录叫 a、命令叫 b」。这是一处可以低成本收紧的地方。**[I]**
- **诊断信息不面向用户——遗漏。** `gaps.ts` 产出的 `runtimes[].missing` 与 `diagnostics` 进了 `skills.catalog` 的返回（[apps/cli/src/skills/rpc.ts](../../apps/cli/src/skills/rpc.ts) 第 7–15、35–48 行），但浏览器侧的 `/` 菜单只用 id、说明与命令（[apps/web/lib/slash.ts](../../apps/web/lib/slash.ts) 第 55–63 行），插件页也没有展示「这个 Skill 在当前运行时缺什么」。规范与三个实现都有「装了但用不全」的可见提示需求；Nema 的数据有了，界面没接。
- **thread 留存按「放不下的第一个起全部丢弃」——简化。** Claude Code 的做法是按最近调用逐个回填到预算上限（文档写「Re-attached skills share a combined budget of 25,000 tokens」，从最近一个开始填）。Nema 的顺序一致（最新在前），但一旦有一条放不下，后面的全部丢掉，而不是跳过它继续尝试更小的。**未实测**这条在实际使用中是否可感知。**[I]**
- **Claude Code 复制整份 Skill 到 `runDir`——刻意。** 原生加载需要文件在磁盘上，而 Nema 不允许 Claude 读用户目录，所以复制一份到一次性的运行目录、再用 `--add-dir` 与 `--settings` 收拢读取范围。代价是 50 MiB 预算与每个任务一次复制；换来的是「Skill 改了不影响正在跑的任务」，与快照语义一致。**[I]**

### 3.4 建议

**值得现在做**

1. 把 `runtimes[].missing` 与 `diagnostics` 接到插件页（或 `/` 菜单的一行说明）：列出「这个 Skill 在当前运行时缺哪些能力」。数据已在 RPC 返回里，只差一处渲染与三语文案。
2. `name` 与目录不一致时，在菜单与插件页给出提示（现在只在内部诊断里）。若不想拒载，至少让用户看到命令名从哪来。

**可以以后做**

3. thread 留存改成「跳过放不下的、继续装下一条」，与 Claude Code 的按预算回填一致，并在进度消息里列出被跳过的 id。
4. 目录预算可配（对应 Codex 的 `skills.max_context_tokens`），让装了很多 Skill 的用户自己调。
5. Skill 目录里的 `references/` 是否要在 `read_skill` 结果里主动列成目录树（现在只列文件名清单，见 `readSkill.ts` 第 16–18 行的 200 个资源上限）。

**不建议做**

6. 执行 Skill 自带的脚本，或按 `allowed-tools` 自动授权工具。这会直接推翻「只给 Room 工具」的边界，属于另一个产品决定，不该由这份对照报告推动。
7. 支持 `context: fork` / 子代理。Nema 没有子代理运行时，标注为缺口比假装支持更诚实。

### 4.2 社区主流做法

- **协议生命周期分三段。** MCP 规范把连接分成初始化（`initialize` + `notifications/initialized`）、运行、关停三阶段；stdio 的关停顺序被明确规定：先关子进程的输入流，等它退出，超时就 `SIGTERM`，再不行 `SIGKILL`；HTTP 的关停是关闭对应连接。<https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle> **[C]**
- **stdio 传输的约束。** 同一规范的传输一节：客户端「launches the MCP server as a subprocess」，消息以换行分隔，stderr 只用于日志，「The client MUST NOT write anything to the server's stdin that is not a valid MCP message」。<https://modelcontextprotocol.io/specification/2025-06-18/basic/transports> **[C]**
- **主流客户端的配置与作用域模型。** Claude Code 把 MCP 服务器放进 `local` / `project` / `user` 三种作用域，项目作用域写 `.mcp.json` 并要求首次使用时批准；`type` 取 `http`（或 `streamable-http`）、`sse`、`ws`、`stdio`；环境变量支持 `${VAR}` 与 `${VAR:-default}` 展开。**并且**：`type: "http"` 的远程服务器由 Claude Code 自己做 OAuth 登录（`/mcp` 或 `claude mcp login`），401/403 会被标成「需要登录」并进入授权流程。<https://code.claude.com/docs/en/mcp> **[C]**
- **stdio 关闭的具体顺序（实现侧）。** Claude Code 在 macOS/Linux 上是 `SIGINT` → 100 ms 后 `SIGTERM` → 再 400 ms 后 `SIGKILL`；Windows 上先关 stdin，300 ms 后再结束进程树。**[C]**
- **插件内的 MCP 服务器自动随会话启动。** 同一文档：启用插件时「Claude Code starts its MCP servers automatically」，会话启动时连接已启用插件的服务器；重载时配置未变的连接保留。**[C]**

### 4.3 差距与原因

- **「重启后不自动恢复」与主流相反——刻意。** Claude Code 的插件 MCP 会随会话自动连接，很多桌面客户端也是「打开就重连」。Nema 的选择是 fail-closed：daemon 启动时不启动任何 MCP 服务器，只清掉上一个 daemon 遗留的副本。理由可以从代码与文档拼出来——MCP 服务器是以用户身份执行的本地进程，自动拉起等于「重启一次就多一批用户没确认过的进程」；`mcpHandlers.ts` 第 44–47 行还写明「如果清理失败，本 daemon 拒绝任何 start，避免两份副本并存」。但这条理由**没有写在 spec 或指南里当成设计决定**，只在 CHANGELOG 第 35 行有一句行为描述。**[I]**
- **stdio 关停顺序与规范有出入。** 规范要求先关 stdin、等退出，再 `SIGTERM`、`SIGKILL`；Nema 直接 `SIGTERM` 进程组，再 `SIGKILL`。`McpStdioTransport.stop` 第 155–180 行没有任何 `stdin.end()`。实际影响：把 stdin 关闭当成关闭信号的服务器（很多 Python SDK 服务器就是这么做的）会被 `SIGTERM` 打断，来不及清理锁文件或状态。这是一处**遗漏**，不是有理由的偏离。**[I]**
- **没有 OAuth——刻意，且已记录去处。** 计划文档 [2026-10-30-extension-mcp-config.md](../superpowers/plans/2026-10-30-extension-mcp-config.md) 第 91 行的「不做」一节写明「远程 MCP 的 OAuth（PKCE、回调、刷新）：CX-06。HTTP 本计划只支持静态请求头凭据；服务器返回 401/403 时状态记为『需要登录』，不尝试登录」。代价是接不了绝大多数云端 MCP（Notion、Sentry、Linear 的官方 MCP 都走 OAuth）。**[C]**
- **不给 Agent 工具——刻意。** 计划第 62–64 行的 D-3 写明这一轮只到「已连接、工具清单与 schema 摘要已记录、页面可见」，交给 Agent 另开计划（命名空间 `mcp__<id>__<tool>`、逐工具启用、schema 变化自动停用、workspace 范围）。主流客户端默认就是把 MCP 工具直接给模型。这条偏离是本产品最显眼的一处，理由（ADR-04 默认拒绝）成立且已记录。**[C]**
- **HTTP 不跟随重定向、不重连——偏严。** `reconnectionOptions.maxRetries: 0` 与 3xx 直接报错，比主流客户端保守（Claude Code 对 HTTP 服务器首次连接的瞬时错误会重试最多三次，会话中断线会退避重连）。这是刻意的：跟随重定向会把 `Authorization` 头带到未预期的地址。**[I]**
- **没有 `list_changed` 处理——遗漏。** 规范定义服务器可以发 `list_changed` 通知表示工具清单变了，Claude Code 会据此刷新。Nema 只在 `doStart` 里 `listTools` 一次（第 211 行），工具清单在连接期间不会更新；页面每几秒轮询的是状态，不是工具清单。**(未核实：Nema 使用的 SDK 1.32.1 是否会把该通知投递给 `Client` 的处理器；这次没有读 SDK 源码验证。)** **[I]**
- **配置作用域只有「这台安装」。** 主流是 local/project/user 三级；Nema 只有一份受管记录，按 workspace 的开关另做（`extensions.useState` 与 hub 侧 workspace 开关）。对单用户场景足够，但项目级共享配置没有位置。**[I]**

### 4.4 建议

**值得现在做**

1. stdio 停止改成规范顺序：`stdin.end()` → 等退出（例如 2 秒）→ `SIGTERM` 进程组 → `SIGKILL`。这是 `McpStdioTransport.stop` 一处小改动，能避免把「等 stdin 关闭」的服务器硬杀。
2. 把「重启后不自动恢复」的理由写进 spec 或指南（现在只有一句行为描述）。它是一条真正的设计决定，应该能和别的偏离一样被引用。

**可以以后做**

3. 处理 `list_changed`：收到通知就重读 `listTools` 并更新状态（依赖 SDK 是否透传，先核实）。
4. 远程 MCP 的 OAuth（CX-06 已立项）。这是接入云端 MCP 的前置条件，不应在这份报告里重新决定范围。
5. 给 HTTP 服务器的首次连接加一次有界的重试（例如 5xx 重试一次），保留「不跟随重定向」。

**不建议做**

6. daemon 启动时自动拉起上次在跑的 MCP 服务器。自动执行用户没确认的本地进程，与当前 fail-closed 的取舍冲突。
7. 把 MCP 工具直接塞给 Agent（D-3 的后续计划有自己的前置条件：逐工具启用、schema 变化停用、workspace 范围）。

### 5.2 社区主流做法

- **「已安装」与「浏览/发现」分开，靠筛选切换。** VS Code 的扩展视图默认同时显示已安装与推荐项，`@installed`、`@recommended`、`@popular`、`@disabled` 等筛选可以叠加（例如 `@installed @category:themes`），另有「Focus on Installed View」只看已安装。<https://code.visualstudio.com/docs/configure/extensions/extension-marketplace> **[C]**
- **先浏览、再看详情、最后选安装位置。** Claude Code 的插件面板：`/plugin` 打开 Discover 标签浏览各 marketplaces 的插件，回车进详情；详情会列出「Will install」的命令、agent、skill、hook 与 MCP/LSP 服务器，官方市场的插件还给出「Context cost」的两个 token 估计；然后选 user / project / local 三种安装作用域。<https://code.claude.com/docs/en/discover-plugins> **[C]**

### 5.3 差距与原因

- **分区与类型筛选与主流基本一致。** 两个区 + 一个类型筛选 + 搜索，是 VS Code 与 Claude Code 的共同骨架；Nema 的差别是把筛选做成一排单选而不是可叠加的查询语法，对四类对象足够了。**[I]**
- **没有「已安装但不可用」的独立视图——遗漏。** VS Code 有 `@disabled`、`@updates`；Claude Code 有 Errors 标签与「Not used recently」。Nema 把「装失败」「配置损坏」「内置运行时缺失」都塞在已安装区的行内提示里（第 379–392、395–403 行），一旦行数多，需要点开的用户不会有入口。数据是有的（`availability`、`error`、`installState`），缺的是一个汇总视图。**[I]**
- **安装前看不到「装上会发生什么」——刻意的一部分。** Claude Code 的详情面板会列出将安装哪些组件和大致 token 成本。Nema 的 `SkillInstallPanel` 只显示来源固定的提交、许可证、找到的 Skill 与目标目录；没有「这个 Skill 会占用多少上下文」或「它声明的能力当前运行时缺哪些」。这与 Skills 一节第 3.3 条是同一个缺口：`gaps.ts` 的数据没接到界面。
- **筛选只在客户端，不随状态同步——刻意。** 主流产品的筛选也会随安装状态变化（例如装完后从 Discover 消失）；Nema 的 `shown` 由 `installState` 派生，安装完成后同一行的 `installState` 变了就会自动换区，但筛选与搜索是本地状态，刷新页面即重置。这与「不发请求」的设计一致，没有实质差距。**[I]**
- **一个入口都没有指向「发现」以外的来源。** Claude Code 有 marketplace 概念（一个目录可以加多个市场）；Nema 的「发现」只有三种：贴链接装 Skill、接本机已有 Skill、手填 MCP 配置。这是刻意的规模选择（不做插件市场），但意味着用户要自己知道来源。**[I]**

### 5.4 建议

**值得现在做**

1. 在已安装区上方加一行汇总（例如「2 个不可用：1 个安装失败、1 个配置损坏」），点了跳到对应行。数据已经在列表里。

**可以以后做**

2. 安装详情里显示该 Skill 在当前运行时的缺口（复用 `skills.catalog` 的 `runtimes`），让用户在点「安装」前就知道装上是「只能用一半」。
3. 把筛选与搜索写进 URL 或本地存储，切换页面后保留（现在刷新即重置）。
4. 安装完成后给一句明确结果（对应 Claude Code 的四种结果：已生效 / 需要配置 / 需要重载 / 加载失败）。

**不建议做**

5. 做插件市场或多来源市场。产品范围没有这个方向，而且会牵出信任与审计。
6. 让筛选与搜索向服务端发请求。当前列表规模下没必要，且会引入新的鉴权面。

## 6. 发布机制第 3 期（tag 只验证，`release-promote` 翻指针）

### 6.1 Nema 现在的做法

- **tag 推三条工作流。** `.github/workflows/npm-publish.yml` 第 13–25 行的触发器是 `push: tags: ['v*']` 加 `workflow_dispatch`（两个输入：`promote_run_id`、`expected_integrity`）；第 43、50 行的 verify 与 build 只在 `promote_run_id == ''` 时运行，所以 tag 推送只做验证与打包冒烟、**不发布**；`.github/workflows/image-publish.yml` 第 25–26 行同样是 tag 推送，第 307 行只推版本 tag（`ghcr.io/nema-project/<name>:<VERSION>`），不再动 `latest`（第 12 行的注释写明 `latest` 交给 `release-promote.yml`）；`.github/workflows/desktop-release.yml` 第 353–375 行的最后一步叫 `Create or reuse draft and upload`，只建/复用 draft 并比对资产集，不发布。
- **晋升由一次人工 dispatch。** `.github/workflows/release-promote.yml` 第 18–25 行的触发器是 `workflow_dispatch`，唯一输入是 `tag`；第 45–69 行的 `authorize` 作业没有写权限，只检查 dispatch 者和重跑者都持有 `maintain` 或 `admin`；第 70–103 行的 `promote` 作业拿到写权限后**第一件事是再查一遍**（因为重跑会复用 authorize 的结果）；第 104–107 行 checkout 的是 `main`（`github.sha`），不是 tag 的代码。
- **tag 只当数据。** 第 111–128 行把 tag 解析成提交、并要求它是 `main` 的祖先（`ahead` 或 `identical`）；第 144–149 行的 `Candidate preflight` 调 `node scripts/release/promote.mjs --preflight`；第 170–174 行调 `promote.mjs` 做实际晋升。
- **脚本里的顺序与判定。** [scripts/release/promote.mjs](../../scripts/release/promote.mjs) 第 29 行稳定版要翻的四个指针是 `npm latest`、`ghcr hub latest`、`ghcr web latest`、`github latest`（预发布只动 `npm next` 与 GitHub Release）；第 101–150 行是 npm 段：absent → dispatch 并等待、same → 已发布、different → 拒绝，并在发布前读 dist-tag 防倒退；第 153 行跑 `verify-release --stage final`；第 158–185 行按 final verify 读到的 digest 移动两个 GHCR `latest`（第 170 行的注释是「同版本但另一个 index 也移动」的判定）；第 187–225 行处理 GitHub Release 的 `--latest`；每次写之前都 `guardTag()` 重验 tag，写完回读确认。
- **promote 不能自己移 dist-tag。** 第 112 行的错误文本写明「promote cannot move a dist-tag (trusted publishing only publishes). A maintainer runs: npm dist-tag add …」——因为 npm 的发布与 `latest` 是同一个动作，OIDC 也不允许事后移动。
- **验证器。** [scripts/release/verify-release.mjs](../../scripts/release/verify-release.mjs) 第 126–137 行把结果分成 `npm`、`images`、`release`、`consistency` 四项，任一项 `missing` 就整体 incomplete、任一项 `unknown` 就 undetermined，退出码不同；第 238 行的用法里 `--stage candidate` 需要 `--expected-integrity`。
- **产物绑定。** `.github/workflows/npm-publish.yml` 第 133–141 行的 publish 作业有 `id-token: write`；第 217 行装 `npm@11.6.2`；第 228–233 行比对 promote 运行留下的 `promote-binding.json`（tag、commit、integrity 三项）；第 251–256 行要求除 tarball 外所有产物文件与 tag 提交逐字节相同；第 308 行 `npm publish --provenance --access public --tag "$dist"`。
- **镜像只做单架构。** `image-publish.yml` 第 182 行 `--platform linux/amd64`，第 183–184 行带 `--provenance=mode=max --sbom=true`。多架构在 [ROADMAP.md](../../ROADMAP.md) 第 123 行列为待办（#50），发布机制设计第 48 行明确「不处理 linux/arm64 镜像（#50）」。
- **发布记录**见 [ROADMAP.md](../../ROADMAP.md) 第 19–38 行：v0.2.0 的 tag 只跑验证，晋升用 `release-promote.yml`，第一次 attempt 因 npm registry 可见性窗口失败并 fail-closed（#158），重跑后成功。

### 6.2 社区主流做法

- **trusted publishing（OIDC）取代长期 token。** npm 文档：可信发布「creates a trust relationship between npm and your CI/CD provider using OIDC」，要求 npm CLI ≥ 11.5.1、Node ≥ 22.14.0；GitHub Actions 需要 `id-token: write`；并且「When you publish using trusted publishing from GitHub Actions or GitLab CI/CD, npm automatically generates and publishes provenance attestations」——`--provenance` 不再是必需的。还建议之后「Require two-factor authentication and disallow tokens」。<https://docs.npmjs.com/trusted-publishers/> **[C]**
- **dist-tag 与发布是两个动作。** npm 文档：「Publishing a package sets the `latest` tag to the published version unless the `--tag` option is used」，而 `npm dist-tag add` 是单独的命令；「Tags that can be interpreted as valid semver ranges will be rejected」。<https://docs.npmjs.com/cli/v11/commands/npm-dist-tag> **[C]**
- **provenance 的含义与局限。** npm 文档：provenance 是「a verifiable link to the package's source code and build instructions」，并明确「it does not guarantee the package has no malicious code」。<https://docs.npmjs.com/generating-provenance-statements/> **[C]**
- **SLSA 的分级口径。** SLSA v1.0 的 Build 轨道：L1 有 provenance、L2 由托管平台签名生成、L3 是加固的构建平台；文档同时标出该页状态为 Retired（描述性概览）。<https://slsa.dev/spec/v1.0/levels> **[C]**
- **不可变 Release 的推荐流程。** GitHub 文档：开启 immutable releases 后「the assets and associated Git tag cannot be changed after publication」，并推荐「1. Create the release as a draft. 2. Attach all associated assets. 3. Publish the draft release」；只有标题、说明、预发布与 latest 状态仍可改。<https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases> **[C]**
- **`gh release create` 不是原子操作。** GitHub CLI 手册：「When you attach assets, `gh release create` creates a draft release, uploads each asset, and then publishes the release. These steps use separate API requests and do not form a single atomic operation.」<https://cli.github.com/manual/gh_release_create> **[C]**
- **GITHUB_TOKEN 触发的事件不会启动新工作流。** GitHub 文档：用仓库的 `GITHUB_TOKEN` 做事时，「events triggered by the `GITHUB_TOKEN` will not create a new workflow run」，例外是 `workflow_dispatch` 与 `repository_dispatch` 总是会。<https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow> **[C]**
- **第三方 action 应钉到完整提交。** GitHub 的安全使用指南建议「Pin actions to a full-length commit SHA」，并说明这是防 action 仓库被植入后门的手段。<https://docs.github.com/en/actions/reference/security/secure-use> **[C]** Nema 的 7 个工作流共 55 处 `uses:`：其中 51 处是外部 action，全部钉了完整 SHA；另 4 处是仓库内的 `./.github/workflows/verify.yml`，不需要钉。注释里还记下 SHA 解析自哪个 tag（例如 `release-promote.yml` 第 34–36 行）。
- **多架构镜像的构成。** OCI 镜像索引规范：`application/vnd.oci.image.index.v1+json`，`manifests` 数组里每个描述符「SHOULD include platform architecture and os」。<https://github.com/opencontainers/image-spec/blob/main/image-index.md> **[C]**
- **多架构怎么构建。** Docker 文档：`docker buildx build --platform linux/amd64,linux/arm64`，产物是 manifest list，拉取时按宿主架构自动选。<https://docs.docker.com/build/building/multi-platform/> **[C]**
- **GHCR 支持 OCI 与 manifest list。** GitHub 文档：容器注册表支持「Docker Image Manifest V2, Schema 2」与「Open Container Initiative (OCI) Specifications」，并支持公开镜像匿名拉取。<https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry> **[C]**

### 6.3 差距与原因

- **「tag 只验证、单独一步晋升」不是 GitHub 官方推荐的形态，但方向一致。** GitHub 推荐「draft → 挂资产 → 发布」，这与 Nema 的 desktop-release（只到 draft）+ release-promote（最后才 `--draft=false`）相同；把 npm 与镜像 `latest` 也放进同一个晋升步骤，是 Nema 的自选动作，官方没有对应物，因为官方没有一个跨注册表的「整套就绪」概念。**[I]**
- **`--provenance` 现在是冗余的——小遗漏。** npm 文档写明用 trusted publishing 时 provenance 自动生成、不需要 `--provenance`。`npm-publish.yml` 第 308 行仍带着这个标志。留着无害（显式声明），但注释或工作流头部没写「这条已由 OIDC 自动完成」，下一个人可能会以为它是必需品。**[C]/[I]**
- **没有 staged publishing / 双人复核。** npm 文档支持 `npm stage publish` + 2FA 审批，并把「stage-only + disallow tokens」称为最大安全姿态。Nema 的选择是「一次 dispatch + maintainer 角色校验」，没有第二人复核，也没有 staged 流程。单维护者项目里这是合理的取舍，但应当作为一条明示的偏离记下来（目前只在 `release-promote.yml` 第 43–44 行的注释里有一句「publishing a release is a maintainer decision」）。**[C]/[I]**
- **单架构镜像是刻意推迟，且有 issue 跟踪。** 设计第 48 行与 ROADMAP 第 123 行都指向 #50；`--platform` 只写一处，改成多架构要动 build、smoke（`localhost` registry 那段）与 publish 三处。这不是遗漏。**[C]**
- **这不是不可变发布——一个真实的缺口。** 2026-10-31 用 `gh release view v0.2.0` 查到的 `isImmutable` 是 `false`，所以这次发布之后 tag 与资产仍可被改动；Nema 的防线全靠工作流在发布前重验 tag，发布之后没有。GitHub 的 immutable releases 正好补这一段，且与「draft → 挂资产 → 发布」的现有流程完全兼容（仓库是否已开启该策略这次没有查到，见第 9 节第 7 条）。**[I]**
- **`release:verify` 的「一致」不等同于「可安装」。** spec 第 103 行已写明它只断言产物存在且彼此一致，不代表测试通过或真机验收。这一点与 SLSA L2/L3 的「provenance 不保证没有恶意代码」是同一类限定，两边都已如实标注。**[C]**
- **失败窗口被接受而非消除。** npm 先动、GHCR `latest` 与 GitHub Release 后动，中间若停下就有一段混合窗口（`scripts/npm/RELEASE.md` 第 86 行写明）。主流做法（例如 staged publish 后一次性 promote）能把窗口压到一次 registry 写入，但跨三个注册表本来就没有原子性。这是有记录的取舍，不是疏漏。**[C]**

### 6.4 建议

**值得现在做**

1. 在仓库设置里开启 immutable releases（GitHub 的 draft → 挂资产 → 发布流程已经就位，见 desktop-release 第 353–375 行）。开启后 `gh release verify` 才有意义，v0.2.0 这样的已发布版本也不会被事后改资产。
2. 在 `npm-publish.yml` 的头部注释里写明「OIDC 可信发布会自动生成 provenance，`--provenance` 是显式冗余」，避免后人误以为必须保留。

**可以以后做**

3. 把「单维护者一次 dispatch，没有第二人复核 / staged publish」这条偏离写进 `scripts/npm/RELEASE.md` 的取舍段，与 #158 的时序缺口放在一起。
4. 评估 npm staged publishing（`npm stage publish` + 2FA 审批）作为可选模式；它需要在 npm 侧改可信发布配置，属于发布流程变更。
5. linux/arm64 多架构镜像（#50）：先改 `image-publish.yml` 第 182 行与 smoke 的本地 registry 段，再改 `promote.mjs` 里「按 digest 移 latest」的假设（它绑定单个 index digest，多架构后仍是单个 index，但要重新验证读取器对嵌套索引的处理，见 [2026-10-30-release-mechanics-phase3.md](../superpowers/plans/2026-10-30-release-mechanics-phase3.md)「与规格不一致、按代码与实测写的地方」第 1 条）。

**不建议做**

6. 让 tag 推送自己发布（回到第 2 期的做法）。这与「tag 只验证、晋升单独授权」的整个第 3 期方向相反。
7. 用 `GITHUB_TOKEN` 链式触发更多工作流来省掉人工 dispatch。`GITHUB_TOKEN` 触发的多数事件不会创建新运行；现有的 `workflow_dispatch` 之所以能工作正是因为它属于例外，再往上叠会依赖脆弱的假设。
8. 为了消除混合窗口而自己发明跨注册表事务。三个注册表之间没有原子性，「失败即停、重跑幂等向前」已经是能给的最强保证。

## 11. 一页结论

- 六块功能里，**与社区最大的一致**是附件的类型白名单与安全下发（OWASP）、Skills 的三级渐进披露（Agent Skills 规范、Claude Code、Codex、Cursor）、以及发布的 OIDC + provenance 基线（npm）。
- **最大的有意偏离**有三处：附件拒绝而不降级；MCP 工具不交给 Agent（D-3）；MCP 重启后不自动恢复。三处都有清楚的「为了保护什么」，但只有前两处把理由写进了文档。
- **最值得马上补的两处**都不是新功能：把 stdio 关停顺序改回规范（一处代码），以及开启 GitHub immutable releases（一个设置）。这两条都不改产品行为。
- **数据已经有、界面还没接**的一处：Skill 的运行时缺口。补上它，插件页与 `/` 菜单才算把「装了但只能用一半」讲清楚。
- **不建议**为了对齐社区而做：执行 Skill 脚本、自动拉起 MCP 服务器、tag 推送自己发布、跨注册表事务。这四件都会推翻已经记录过的取舍。
