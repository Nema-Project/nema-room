# Desktop tool payload provenance

`tools-manifest.json` is the trusted build-time pin set for Node.js 24.22.1 and the dugite-native 2.56.0-1 release. Each target maps to a versioned official artifact URL and a SHA-256 value recorded by Node.js's checksum manifest or the upstream dugite-native release. The downloader does not discover versions dynamically and does not accept checksum values from a downloaded payload.

`fetchTools({ platform, arch, cacheDir, outDir })` returns paths relative to `outDir`. It writes `outDir/<platform>-<arch>/node/`, `git/`, `licenses/git/` when needed, and `tools-source.json`; those directories retain the full extracted distributions, including their bundled docs, license trees, and notices. macOS Git archives include the upstream `libexec/git-core/NOTICE` but no Git license text, so the fetcher adds the exact `COPYING` file from the Git source commit pinned by dugite-native v2.56.0-1's `git` submodule and verifies its committed SHA-256. The `licenses` return value identifies Node's LICENSE, Git's license text and notice, Git's retained distribution tree, and the generated provenance record. Cache and output directories must be separate. Existing target output is refused. Publication reserves the final path with exclusive directory creation and a private ownership token; cleanup removes that path only while its token and directory identity still match.

This is a build-time fetch only. An app runtime must consume the staged relative paths and must fail if its bundled executables are missing. No fetch or host Node/Git fallback belongs in application first launch. Windows x64, macOS arm64/x64, and Linux x64/arm64 artifacts are pinned; the Linux entries support local-Web payload staging and do not promise a Linux desktop installer or all Linux distributions.

The pinned Git distribution includes Git, Git for Windows, Git LFS, Git Credential Manager, and upstream-provided supporting components. The full upstream distribution and all included notice/license trees are retained rather than reducing it to `git` alone. `package-versions.txt` records the upstream release's component versions; `tools-source.json` repeats target-specific source URLs, source commit, archive names and hashes in each generated output. Node's archive also includes npm and Corepack, whose versions are recorded.

**Source-correspondence review is pending.** The pinned source and original license material are retained as evidence, but this package does not claim that source correspondence or all redistribution obligations have been satisfied. Task 7c must resolve and gate those requirements before any public release. This note is an implementation status, not a legal conclusion.

## Managed payload staging

Run `npm run desktop:stage` on the target native platform. It builds a sanitized source snapshot with the bundled Node/npm, then stages `dist/desktop/<platform>-<arch>/`. The snapshot excludes `.git`, all `.env*` files, ignored build output and user state. Its `npm ci` cannot discover checkout environment files. The managed Next build uses `NEMA_MANAGED_LOCAL_BUILD=1` and `NEXT_PUBLIC_NEMA_LOCAL=1` to select standalone output and same-origin UI/API/EventSource/diagram routes. Developer and Compose builds retain their existing root `.env` behavior.

The payload uses `runtime-manifest.json` schema 1. `node`, `git`, `coreEntry`, `cliEntry`, `webEntry`, and `licenses` are forward-slash relative paths from the payload root. Compiled workspace packages, production dependencies, migrations, PGlite WASM, the report skill, vendored archify and superpowers rules, full Next standalone output, `.next/static`, public assets, and complete Node/Git distributions stay under that root. `tools-source.json` preserves `sourceCorrespondence.status: "pending-task-7c"`; staging does not imply the later source correspondence review is complete.

Staging refuses an existing target, version or native target mismatch, missing runtime assets, unsafe paths, links that escape the source tree, and missing license/notice material. The documented CLI accepts `--platform <win32|darwin|linux> --arch <x64|arm64> --out <dir> [--source-root <dir>]`; the positional `<sourceRoot> <outputDir>` form remains available for existing automation. Only the current native target can be built locally.

The staged payload includes native browser launchers (`Nema Browser.cmd`, `Nema Browser.command`, or `nema-browser`) that call the bundled Node and compiled local core. Browser mode issues a verified loopback ticket URL and delegates opening to the fixed OS browser command. `--no-open` is the automation seam; it prints the ticket URL without launching a browser. The managed Next entry requires a private IPC channel from its owning core so a hard core exit closes the production listener independently of the launcher's readiness IPC.

## Electron desktop packaging

`apps/desktop` pins Electron `45.0.0` and electron-builder `26.18.0` exactly in its package manifest and the root npm lockfile. `npm run desktop:make -- --platform win32 --arch x64` builds the native staged runtime and packages Windows x64 NSIS installer plus a portable ZIP under `dist/desktop-artifacts/win32-x64/`. Native macOS x64/arm64 builds produce DMG and ZIP; this command rejects cross-platform builds. `--stage-out <dir>` and `--out <dir>` select distinct output paths. `--staged <payload-dir>` accepts only an existing staged manifest that matches the explicit app version and native target, for a repeat packaging pass without rebuilding the source snapshot.

The Electron app loads only the authenticated loopback URL from `ensureLocalRuntime`, with its staged `payload/` in `process.resourcesPath` outside ASAR. It does not implement Hub, DB, settings or daemon business logic. Window close destroys the window while leaving Electron, tray and core running; activation obtains a fresh launch ticket. `Quit Nema` invokes the shared authenticated shutdown request and waits for the private HMAC-bound completion receipt written only after runtime teardown and lease/control closure. A failed drain reports the bounded error and leaves the app open for recovery/browser fallback. The browser launcher accepts `--quit` to request that same authenticated operation without Electron.

Electron's `LICENSE` and `LICENSES.chromium.html` are staged at `runtime/licenses/electron/` inside the payload. The source-material collector inventories both files, and desktop publication validation requires them and cross-checks their hashes against the inventory. The app package also retains the application's MIT license in the payload. Windows signing is disabled. macOS requests explicit ad-hoc signing with identity `-` and `hardenedRuntime: false`; this is not Developer ID signing or notarization. NSIS differential-package generation is disabled; no update feed or auto-update client is configured.

`npm run desktop:smoke` extracts the portable Windows package into a UUID-scoped path containing spaces and Japanese characters, uses separate temporary Electron user-data and local-core homes, and launches the copied executable. It checks authenticated readiness, production CSS/fonts, a persisted workspace/chat using a local fake Responses provider, browser fallback after an Electron main-process exit, and data after authenticated core restart. The smoke intentionally leaves the final copied app/core running for visible acceptance. `NEMA_DESKTOP_TEST_HOME` and `NEMA_DESKTOP_TEST_USER_DATA` are process-only smoke overrides; production defaults use the existing `~/.nema/desktop` data home and Electron's ordinary user-data directory.

Windows x64 staging also builds `apps/cli/native/windows/owned-helper.c` with the native Clang toolchain and stages `runtime/owned-helper.exe`, referenced as `ownedHelperGuardian` in schema 1. Set `NEMA_WINDOWS_NATIVE_CC` to an explicit `clang.exe` path when it is not on the build shell's PATH. The compiler is a build-time dependency only; first launch reads the staged guardian and never compiles or downloads it. The guardian uses a current-user-only local pipe lease and a private Windows Job Object for each managed helper. The POSIX helper ownership implementation and native macOS/Linux process proof remain separate release gates; no POSIX cleanup guarantee is made by this Windows component.

Fixture tests (`node --test scripts/desktop/staging.test.mjs`) validate layout and failure boundaries. `npm run desktop:smoke-runtime -- <payload>` exercises the actual staged payload with a temporary home, fake local Responses provider, and bundled Node/Git; it does not substitute for the full native stage or publication/provenance review.

## Source materials and release eligibility

`source-materials.mjs` inventories the staged Node/Git trees, application and Electron notices, vendored notices, production dependency license files, and generated font assets. It records `etc/package-versions.txt` and a sorted Git distribution file-set fingerprint so the MinGit package closure can be reconciled against the files actually shipped. It copies notices and upstream source archives/recipes into an inspectable bundle without extracting or executing them. Remote downloads are HTTPS-only, allowlisted to primary upstream hosts, immutable-ref-bound, and capped at 256 MiB each. Use `npm run desktop:collect-source-materials -- <payload-root> <ignored-bundle-output> <platform-arch> <app-version> <source-plan.json>`.

A source plan may set `inputRoot` to a relative directory under the directory containing that plan. Local `sourcePath` entries for archives or notices are resolved relative to `inputRoot`; paths must remain inside that root and symlink/junction ancestors are rejected. Omit `inputRoot` for URL-only plans. The five-argument CLI form is unchanged; it does not infer a local input root from the working directory.

The schema-1 `source-materials.json` records archive paths relative to the bundle, SHA-256, target/tool/version, immutable upstream refs, notice hashes/provenance, tool archive pin comparisons, staged font hashes, and MinGit package/file-set inventory. `pending` is an allowed local inventory state. The collector does not convert a downloaded archive or a license notice into verified binary correspondence. Windows MinGit requires a reconciled complete MSYS2/MinGW package source set, patches, and exact build recipes; generated Inter and JetBrains Mono WOFF2 files require exact upstream revision mapping. Those unresolved entries keep publication blocked.

Task 10 release collection must place the validated `source-materials.json` and referenced archives in the candidate release payload, then invoke `npm run desktop:validate-release -- <payload-root> <platform-arch> <app-version>` before publishing. That validator checks the payload runtime manifest, exact target/version, Node/Git archive names and SHA-256 values against `tools-manifest.json`, the staged `tools-source.json`, every material path/hash and immutable ref, the complete notice inventory, the package-version/file-set fingerprint, and required component categories. Missing, unsafe, pending, mismatched, or incomplete material fails closed. Local staging continues to accept `pending-task-7c` and the documented `source-materials-collected` provenance label; neither label alone enables release eligibility.
