# Desktop tool payload provenance

`tools-manifest.json` is the trusted build-time pin set for Node.js 24.22.1. Each target maps to a versioned official artifact URL and a SHA-256 value recorded by Node.js's checksum manifest. The downloader does not discover versions dynamically and does not accept checksum values from a downloaded payload.

`fetchTools({ platform, arch, cacheDir, outDir })` returns paths relative to `outDir`. It writes `outDir/<platform>-<arch>/node/` and `tools-source.json`; the Node directory retains the full extracted distribution, including its docs, license and notices. The `licenses` return value identifies Node's LICENSE and the generated provenance record. Cache and output directories must be separate. Existing target output is refused. Publication reserves the final path with exclusive directory creation and a private ownership token; cleanup removes that path only while its token and directory identity still match.

This is a build-time fetch only. An app runtime must consume the staged relative paths and must fail if its bundled Node is missing. No fetch or host Node fallback belongs in application first launch. Windows x64, macOS arm64/x64, and Linux x64/arm64 artifacts are pinned; the Linux entries support local-Web payload staging and do not promise a Linux desktop installer or all Linux distributions.

Git is not bundled. Nema runs the user's own git, so `fetch` uses their credential helpers and SSH setup; `ensureLocalRuntime` refuses to start a core unless `git --version` reports 2.31 or later and shows install guidance instead (`apps/cli/src/systemGit.ts`). A Mac app opened from Finder also looks in `/opt/homebrew/bin`, `/usr/local/bin`, and `/opt/local/bin`. The desktop smokes put the host git's directory on the app's minimal PATH. Node's archive includes npm and Corepack. Their versions are recorded in `tools-source.json`. The tool cache keeps `include/`, npm, and Corepack for the staging `npm ci`. The shipped payload omits them.

**Publication notices.** Node (MIT) is accepted from the LICENSE inside the staged Node distribution. Inter and JetBrains Mono (OFL) are accepted from the OFL texts collected with the WOFF2 files. Electron's ffmpeg is LGPL: `LICENSES.chromium.html` must name ffmpeg and LGPL v2.1, and `ffmpeg.dll` or `libffmpeg.dylib` must remain a separate file in the Electron distribution so it can be replaced. This is an implementation gate, not a legal opinion.

## Managed payload staging

Run `npm run desktop:stage` on the target native platform. It builds a sanitized source snapshot with the bundled Node/npm, then stages `dist/desktop/<platform>-<arch>/`. The snapshot excludes `.git`, all `.env*` files, ignored build output and user state. Its `npm ci` cannot discover checkout environment files. The managed Next build uses `NEMA_MANAGED_LOCAL_BUILD=1` and `NEXT_PUBLIC_NEMA_LOCAL=1` to select standalone output and same-origin UI/API/EventSource/diagram routes. Developer and Compose builds retain their existing root `.env` behavior.

The payload uses `runtime-manifest.json` schema 1. `node`, `coreEntry`, `cliEntry`, `webEntry`, and `licenses` are forward-slash relative paths from the payload root. Compiled workspace packages, production dependencies, migrations, PGlite WASM, the report skill, vendored archify and superpowers rules, full Next standalone output, `.next/static`, public assets, and the Node runtime without headers, npm, or Corepack stay under that root. `tools-source.json` preserves `sourceCorrespondence.status: "pending-task-7c"`; staging does not imply the later source correspondence review is complete.

Staging refuses an existing target, version or native target mismatch, missing runtime assets, unsafe paths, links that escape the source tree, and missing license/notice material. The documented CLI accepts `--platform <win32|darwin|linux> --arch <x64|arm64> --out <dir> [--source-root <dir>]`; the positional `<sourceRoot> <outputDir>` form remains available for existing automation. Only the current native target can be built locally.

The staged payload also includes a CLI launcher (`Nema CLI.cmd`, `Nema CLI.command`, or `nema-cli`) that runs the bundled Node on the bundled CLI entry, forwards every argument and preserves the exit code; run `Nema CLI.cmd report install --agent claude` from the payload folder (`resources/payload` in an installed app) so the hooks record the bundled Node and CLI paths. The staged-payload smoke (`desktop:smoke-runtime`) is meant to run `report install --help` through it; that check has not been run against a rebuilt payload yet. The staged payload includes native browser launchers (`Nema Browser.cmd`, `Nema Browser.command`, or `nema-browser`) that call the bundled Node and compiled local core. Browser mode issues a verified loopback ticket URL and delegates opening to the fixed OS browser command. `--no-open` is the automation seam; it prints the ticket URL without launching a browser. The managed Next entry requires a private IPC channel from its owning core so a hard core exit closes the production listener independently of the launcher's readiness IPC.

## Electron desktop packaging

`apps/desktop` pins Electron `45.0.0` and electron-builder `26.18.0` exactly in its package manifest and the root npm lockfile. `npm run desktop:make -- --platform win32 --arch x64` builds the native staged runtime and packages the Windows x64 NSIS installer under `dist/desktop-artifacts/win32-x64/`. Native macOS arm64 builds produce a DMG (Intel Macs are not supported); releases ship only these installers; this command rejects cross-platform builds. `--stage-out <dir>` and `--out <dir>` select distinct output paths. `--staged <payload-dir>` accepts only an existing staged manifest that matches the explicit app version and native target, for a repeat packaging pass without rebuilding the source snapshot.

The Electron app loads only the authenticated loopback URL from `ensureLocalRuntime`, with its staged `payload/` in `process.resourcesPath` outside ASAR. It does not implement Hub, DB, settings or daemon business logic. Window close destroys the window while leaving Electron, tray and core running; activation obtains a fresh launch ticket. `Quit Nema` invokes the shared authenticated shutdown request and waits for the private HMAC-bound completion receipt written only after runtime teardown and lease/control closure. A failed drain reports the bounded error and leaves the app open for recovery/browser fallback. The browser launcher accepts `--quit` to request that same authenticated operation without Electron.

Electron's `LICENSE` and `LICENSES.chromium.html` are staged at `runtime/licenses/electron/` inside the payload. The source-material collector inventories both files, and desktop publication validation requires them and cross-checks their hashes against the inventory. After pack, other `LICENSES.chromium.html` copies in the app are removed; the payload copy stays. Source maps and `node_modules/sharp` / `node_modules/@img` are not shipped. The managed Next build sets `images.unoptimized`. Staging prints payload section sizes and writes `payload size warning:` when a budget is exceeded; that warning does not fail the build. `node scripts/desktop/payload-size.mjs <payload>` prints the same report. The app package also retains the application's MIT license in the payload. Windows signing is disabled. macOS requests explicit ad-hoc signing with identity `-` and `hardenedRuntime: false`; this is not Developer ID signing or notarization. NSIS differential-package generation is disabled; no update feed or auto-update client is configured.

`npm run desktop:smoke -- --installer <exe>` silently installs the Windows NSIS package (`/S /D=`) into a UUID-scoped path containing spaces and Japanese characters, failing if the installer does not finish within 15 minutes and reporting how long it took. It uses separate temporary Electron user-data and local-core homes and launches the installed executable. It checks authenticated readiness, production CSS/fonts, a persisted workspace/chat using a local fake Responses provider, browser fallback after an Electron main-process exit, and data after authenticated core restart. Run locally, the smoke leaves the final app/core running for visible acceptance; with `CI` set it shuts them down. The silent install registers a per-user uninstall entry and shortcuts, so run it on a disposable machine. `NEMA_DESKTOP_TEST_HOME` and `NEMA_DESKTOP_TEST_USER_DATA` are process-only smoke overrides; production defaults use the existing `~/.nema/desktop` data home and Electron's ordinary user-data directory.

Windows x64 and macOS arm64 staging also download the Graphify runtime pinned in `graphify-lock.json`: CPython 3.11.17 from the python-build-standalone `20261021` release, and graphifyy 0.9.95 with its pinned wheels and no extras. SHA-256 is checked before extract. The Windows launcher is compiled from `graphify-launcher.c` during staging; the macOS launcher is a shell script. Windows runs `python\python.exe -m graphify`. macOS runs `python/bin/python3.11 -m graphify`. Duplicate `python` and `python3` copies are not shipped. `libpython3.11.dylib` is removed only when no Mach-O file in that tree loads it; Windows Python DLLs stay. The lockfile keeps tree-sitter for JavaScript, TypeScript, TSX, Python, Go, Rust, Java, C, C++, C#, Ruby, PHP, Swift, Kotlin, Bash, and JSON. Verilog, Fortran, Julia, Elixir, Groovy, Lua, Objective-C, PowerShell, Scala, and Zig wheels are not installed. YAML, TOML, HTML, CSS, and Markdown have no grammar wheel in graphifyy 0.9.95. A missing grammar is a per-file warning; `extract --code-only` still exits 0. Archive symlinks are copied out so the payload contains no links and no build-machine home path. Licenses land in `tools/graphify/licenses/` and `runtime/licenses/graphify-runtime/`. This is a build-time fetch. First launch does not download Graphify, uv, or Python. Linux staging is not a desktop release target and does not receive this pin. The pin's `sourceCorrespondence.status` stays `pending-task-7c`.

Windows x64 staging also builds `apps/cli/native/windows/owned-helper.c` with the native Clang toolchain and stages `runtime/owned-helper.exe`, referenced as `ownedHelperGuardian` in schema 1. Set `NEMA_WINDOWS_NATIVE_CC` to an explicit `clang.exe` path when it is not on the build shell's PATH. The compiler is a build-time dependency only; first launch reads the staged guardian and never compiles or downloads it. The guardian uses a current-user-only local pipe lease and a private Windows Job Object for each managed helper. The POSIX helper ownership implementation and native macOS/Linux process proof remain separate release gates; no POSIX cleanup guarantee is made by this Windows component.

Fixture tests (`node --test scripts/desktop/staging.test.mjs`) validate layout and failure boundaries. `npm run desktop:smoke-runtime -- <payload>` exercises the actual staged payload with a temporary home, fake local Responses provider, and the bundled Node plus the system Git; it does not substitute for the full native stage or publication review.

## Source materials and release eligibility

`source-materials.mjs` inventories the staged Node tree, application and Electron notices, vendored notices, production dependency license files, and generated font assets. An MIT package that ships the license grant in its README and no separate license file uses that README as the notice. It copies notices and upstream source archives/recipes into an inspectable bundle without extracting or executing them. Remote downloads are HTTPS-only, allowlisted to primary upstream hosts, immutable-ref-bound, and capped at 256 MiB each. Use `npm run desktop:collect-source-materials -- <payload-root> <ignored-bundle-output> <platform-arch> <app-version> <source-plan.json>`.

A source plan may set `inputRoot` to a relative directory under the directory containing that plan. Local `sourcePath` entries for archives or notices are resolved relative to `inputRoot`; paths must remain inside that root and symlink/junction ancestors are rejected. Omit `inputRoot` for URL-only plans. The five-argument CLI form is unchanged; it does not infer a local input root from the working directory.

The schema-1 `source-materials.json` records archive paths relative to the bundle, SHA-256, target/tool/version, immutable upstream refs, notice hashes/provenance, tool archive pin comparisons, and staged font hashes. A component whose policy obligation is `notice` is satisfied by the named license file, not by a source archive. Node, the two fonts, and Electron's ffmpeg are notice obligations. A source-archive obligation still has to be hash-bound. Missing, unsafe, or mismatched material fails closed.

Task 10 release collection must place the validated `source-materials.json` in the candidate release payload, then invoke `npm run desktop:validate-release -- <payload-root> <platform-arch> <app-version>` before publishing. That validator checks the payload runtime manifest, exact target/version, the Node archive pin, the staged `tools-source.json`, the notice inventory against `source-materials-policy.json`, and the package-version/file-set fingerprint. Local staging continues to accept `pending-task-7c` until collection marks the payload `source-materials-collected`.

## Brand assets

Regenerate committed Nema Room resources with `node scripts/desktop/build-brand-assets.mjs` after `npm ci`. The script resolves sharp from Next's existing dependencies and exports from `docs/design/brand/nema-room-mark.svg`. It does not invoke image generation. Desktop assets are included in ASAR; ICO/ICNS configure the platform icons. Display names use Nema Room; `Nema.exe`, appId and the `Nema-<version>-<platform>-<arch>` artifact prefix stay unchanged for launcher compatibility. See the [brand notes](../../docs/design/brand/README.md).
